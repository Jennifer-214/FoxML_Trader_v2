# v5.10 Design Notes

**Purpose:** captured-but-not-yet-scheduled design ideas for ML pipeline
extensions, surfaced during the v5.9 ML Hardening sprint. NONE of these
are committed; this doc is a parking lot for "good ideas worth designing
later" so they don't get lost between sprints.

When opening a v5.10+ plan: read this doc, decide what's in scope, copy
the relevant section into the plan with concrete deliverables. Items
here are pre-design — effort estimates are rough.

---

## Idea 1: Parallel hyperparameter search (grid training)

**Origin:** 2026-05-02 paper-test session. Operator observed that backtest
training spawns 4 cores but only one collects features for training; the
other 3 do CPU work for nothing.

### What it would do

Run training as a 4-core grid search:
- core_0_label_tp_pct=0.01, core_1_=0.03, core_2_=0.05, core_3_=0.07
- Each core trains its OWN XGBooster on its OWN feature_matrix slice
- Post-train: compare per-core val accuracy on a SHARED held-out test set
- Operator picks the winning configuration OR ensemble blends all 4

### Why this is interesting

- 4× faster wall-clock for hyperparameter sweeps
- Reuses existing per-core override architecture (`PER_CORE_OVERRIDE_FIELDS`)
- Currently the OPTIMIZER tab does this serially — moving to parallel is
  pure throughput win
- Aligns with how production ML teams sweep barriers / TP percentages
  for label engineering

### Why this is risky

- **Overfitting via configuration selection.** Testing 4 cfg values
  vs 1 multiplies the chance of a "lucky" model that LOOKS good on
  held-out by random noise. Mitigation: triple-split (train / validate
  for grid selection / test for final calibration). Held-out test set
  is locked + only the winning configuration's metric goes on its
  stamp.
- **Stamp + scaler artifact multiplication.** 4 sets of `<model>.bin
  + .stamp + .scaler` per training run. Operator workflow gets noisier.
  Mitigation: foxml suite UI shows the comparison table + lets operator
  delete losers in one click.
- **Ensemble inference adds parity surface.** Loading 4 models at
  inference + blending predictions = 4× the v5.9.3 scaler verification
  surface. Mitigation: ship single-best-deployment first; ensemble as
  a separate v5.11 feature with its own design pass.

### Suggested first ship (v5.10 phase A)

**"Parallel grid search, single-best deployment" (~1-2 days):**

1. Per-core feature collection — `BacktestSharded_Run` writes to per-core
   `feature_matrix[core_id]` instead of shared.
2. Train Model worker iterates: for each core 0..N, train an XGBooster
   on that core's matrix using the per-core resolved cfg.
3. Post-train: write 4 model files at `<model_dir>/grid_<core>/<role>.bin`
   (suffix per core); the operator picks the winner via UI.
4. Held-out evaluation: 1 shared test set, 4 models evaluated against it
   independently. Display per-model held-out metric + gap.
5. "Promote winner" button: copies winning core's model + stamp + scaler
   to the canonical deploy location; deletes losers.

### Suggested follow-up (v5.11+ phase B)

**"Live ensemble" (3-5 days):**

1. Engine loads 4 models at boot (zoos[i].grid_models[0..3])
2. At inference, all 4 predict; final output is `bandit_blend(predictions,
   weights)` where weights come from a Bandit-Exp3 (already partially in
   v5.6 cfg).
3. ConfidenceScorer per-model — track IC for each ensemble member
   independently.
4. Stamp body extends with `grid_member_count=N` + per-member SHA list.
5. Sidecar handling: 4× scalers, all must verify; refuse-or-warn pattern
   carries.

### Out of scope for any near-term ship

- Online ensemble weight updates (continual learning) — breaks the
  "models load once at boot" invariant; defer to whenever live
  hot-swap becomes a feature.
- Cross-symbol ensemble — different shape problem; deferred until
  multi-symbol support lands.

## Idea 2: `FOREACH_TARGET` X-macro retrofit for labels

**Origin:** v5.9.2a snapshot test discipline. Currently `label_table[]`
in `Backtest/LabelFunctions.hpp` is hand-maintained. No
`LABEL_REGISTRY_HASH` exists. v5.9.2a snapshot tests are the SOLE
protection against label body drift. Mentioned in
`CLAUDE_ML_INVARIANTS.md` as deferred to v5.10+.

### What it would do

Same shape as v5.8.1b's `FOREACH_FEATURE(X)` for features:

```cpp
#define FOREACH_TARGET(X) \
    X(WIN_LOSS,           "win_loss",           1, 0,  Label_WinLoss,        "Binary: profitable entry") \
    X(BARRIER,            "barrier",            1, 0,  Label_Barrier,        "First-passage 0/0.5/1") \
    X(FORWARD_PNL,        "forward_pnl",        1, 1,  Label_ForwardPnl,     "% return over N ticks") \
    X(PEAK_VALLEY_STABLE, "peak_valley_stable", 1, 3,  Label_PeakValleyStable, "3-class softmax") \
    ...
```

X-macro generates: `LABEL_*` enum constants, `label_table[]`, `LABEL_NAMES[]`,
**`LABEL_REGISTRY_HASH()` constexpr** that flips on row add/remove/reorder
or version bump.

### Why this is interesting

- Closes the structural protection gap — body changes still need
  snapshot tests, but at least add/remove/reorder gets caught at the
  hash layer without snapshot updates
- Adds `label_registry_hash` to stamp body → cross-binary catches
  "model trained on different label set" at engine load time
- Standardization with FOREACH_FEATURE makes the codebase pattern
  consistent

### Suggested ship

**~3-4h sprint:**

1. Convert `label_table[]` to X-macro emit (auto-generated body)
2. Add `LABEL_REGISTRY_HASH()` constexpr (FNV-1a of names + versions)
3. Extend stamp body with `label_registry_hash` field (forward-compat
   per v5.8.6 pattern)
4. Verifier checks at load — refuse-or-warn pattern per
   `held_out_gate_strict`
5. v5.8.8-style round-trip test extends

## Idea 3: Drift detection / model retirement

**Origin:** v5.9.4 ML_TEST_RECIPES.md "Retraining cadence" section
mentions drift but doesn't automate it. Today the operator has to
manually check ML Status panel's `ml_confidence_ic` periodically.

### What it would do

Engine tracks rolling IC over time (already does via ConfidenceScorer).
Adds a cfg threshold + automated trigger:

```
confidence_ic_floor = 0.02      # below this, model considered stale
confidence_ic_floor_window = 86400  # seconds; sustained-below required to fire
```

When IC stays below floor for the window, engine emits a CRITICAL log
+ optionally enters `kill_switch=1` (refuse new entries) until operator
acknowledges. Configurable response:
- `auto_kill_on_drift=1` — automatic kill switch
- `auto_kill_on_drift=0` — warn only

### Why this is interesting

- Closes the "model degraded but no one noticed" silent-failure class
- Reuses existing ConfidenceScorer infrastructure
- Operator gets a definite signal rather than "I should check
  weekly maybe"

### Why this is risky

- Auto-kill-on-drift IS new behavior — operator might be surprised
  on a quiet market day where IC dips below floor without real
  degradation
- Threshold tuning is empirical; defaults will be wrong for some
  symbols/configs

### Suggested ship

**~4-5h:**

1. ConfidenceScorer extension: rolling IC over windowed history
2. Cfg fields + parser
3. Engine boot wires the trigger
4. ML Status panel: "drift: 0.018 IC below floor for 12h" red row
5. Tests: drift-detected fires correctly; healthy IC doesn't trigger

## Idea 4: Multi-horizon prediction

**Origin:** Currently labels predict single forward horizon (e.g.
`label_forward_ticks=1000`). Models could predict at multiple horizons
+ ensemble.

### What it would do

Train 3-5 models at horizons [100, 500, 1000, 5000, 20000] ticks. At
inference, predict at all horizons. Use the prediction with highest
confidence (lowest forward-uncertainty) for entry decisions.

### Why this is interesting

- Different market microstructure regimes operate at different time
  scales; a single horizon can't capture all
- Ensemble improves robustness to horizon-specific noise

### Why this is risky

- Adds 3-5× the inference cost (multiple `Model_Predict` calls)
- 3-5× the parity surface (multiple stamps, multiple scalers)
- Horizon selection at inference is heuristic — needs validation

### Suggested ship

**~5-7h, optional after Idea 1 (parallel grid):**

The grid-search infrastructure from Idea 1 covers most of the
machinery (per-core training, per-core stamps). Multi-horizon is
just a different per-core variable (label_forward_ticks instead of
label_tp_pct).

## Idea 5: Feature mask cfg per-core

**Origin:** Current `FOREACH_FEATURE` X-macro disables features at
COMPILE time only. Operators may want to disable a feature for ONE
core (e.g., regime model uses everything, barrier model uses only
short-window features) without recompiling.

### What it would do

Add `feature_mask` cfg field — a 64-bit field where bit N enables
FEATURE_N. Per-core override. `Features_PackAll` checks the mask
before invoking each compute fn; masked-off features pack as 0 (or
get NaN'd via the existing -1 sentinel path).

### Why this is interesting

- Per-role feature subsetting without recompile
- Operator can A/B test "does barrier model do better with fewer
  features?" cheaply

### Why this is risky

- Models trained against feature mask A WILL diverge from feature
  mask B — masking is a feature-set change, requires retrain
- Forces FEATURE_REGISTRY_HASH to incorporate the mask if we want
  drift detection. Either bake mask into stamp + verify, or accept
  that stamp's hash assumes "all features enabled" and operators
  must keep masks consistent

### Suggested ship

**~3-4h, but design first:**

Big design question: is the mask part of the stamp's
`feature_registry_hash`, or a separate stamp field that's checked
at load? Either works; the choice affects how operators reason
about feature-set drift.

## Idea 6: Auto-stamp from training worker

**Origin:** v5.9.3b's training worker computes + persists scaler but
DOESN'T emit stamp. Operator must manually run `tools/stamp_model.sh`
with the SHA from the worker log. v5.9.4 deferred auto-stamp to "post-
v5.9 cleanup ship."

### What it would do

`train_model_worker_fn` post-persist: pick up cfg's `auto_stamp_secret`
+ training metrics + scaler SHA + feature_registry_hash, call
`stamp_write_for_model` directly. Operator gets a fully-stamped
artifact bundle without the manual CLI step.

### Why this is interesting

- Closes the v5.9.3b operator-friction gap (the "(model_path empty?)"
  message we just fixed)
- Reduces total operator clicks per train: from 2 (train, then stamp
  CLI) to 1 (train)
- Aligns with v5.3.2's existing auto-stamp wiring (currently used
  by `Backtest_RunFullValidation` but not by Train Model)

### Why this is risky

- Need a secret. Either pin via cfg (held_out_stamp_secret already
  exists) or via env var. Storing in cfg = secret in config files;
  worth thinking through.
- Auto-stamp behavior on training failure: should never write a
  stamp if the model didn't validate cleanly. v5.9.3b's Gap G
  contract covers this.

### Suggested ship

**~1-2h, low risk:**

Reuse the existing v5.3.2 auto-stamp gate. Just thread it through
the Train Model worker too. Mostly a cfg + parameter-passing chore.

## Idea 7: Scaler comparison / compatibility check

**Origin:** v5.9.3 scaler binds to a specific training set. Operators
who retrain on Tuesday's data and Wednesday's data get two scalers
that both pass v5.9.3a's verification but produce slightly different
inference outputs.

### What it would do

Tool: `tools/compare_scalers.sh <a.scaler> <b.scaler>` prints diff:

```
Mean diff per feature:
  FEATURE_SHORT_SLOPE: 0.0001 → 0.0003 (Δ +0.0002, 200%)
  ...
Stddev diff per feature:
  FEATURE_VWAP_DEV: 0.05 → 0.06 (Δ +20%)
  ...
Operator decision: features with Δ > 50% may indicate market regime shift.
```

Helps operator decide whether to deploy the new scaler or keep the
old one.

### Suggested ship

**~2h, low-priority polish:**

Mostly a CLI tool over the existing FeatureStandardizer_Load.

## Idea 8: WF + Train per-class accuracy breakdown

**Origin:** v5.9.4a Phase 3 added baseline awareness, but per-fold
display doesn't show per-class accuracy for multiclass. For
PEAK_VALLEY_STABLE, "47% accuracy" hides whether it's "good at peak,
bad at valley" or "balanced across classes" — different actionable
states.

### What it would do

Per-fold table extends with per-class accuracy columns when
`label_kind == 2` (multiclass). For 3-class:

```
Fold  Train  Val   Gap   c0Acc  c1Acc  c2Acc  Status
2     53.6%  42.9% 10.7%  3%     74%    52%    weak c0
3     44.9%  47.4% -2.5%  5%     68%    51%    weak c0
...
```

### Suggested ship

**~2-3h, polish:**

Requires extending `WalkForwardResults` struct with per-fold per-class
arrays. Display logic is ~30 LOC.

## Idea 9: Snapshot test suite for ConfidenceScorer

**Origin:** v5.9.2a added snapshot tests for features + labels +
strategy gates. ConfidenceScorer formula has its own test (Sub-area
2a) but only tests 4 input combinations. A more comprehensive suite
would catch any future formula tuning.

### What it would do

Snapshot test that exercises the full ConfidenceScorer state machine:
push N predictions through, check IC + RMSE values match recorded
snapshot at each step. Catches changes to RollingIC, RollingRMSE,
freshness math.

### Suggested ship

**~1-2h, low-risk polish:**

Same pattern as v5.9.2a's existing tests, just more coverage.

## Idea 10: Cross-binary build flag fingerprinting

**Origin:** v5.9.4 documented build flag drift as "operator
discipline" (PARITY_LIFECYCLE.md). Could be enforced via stamp
fingerprinting.

### What it would do

Stamp body field `build_flags=<hex>` containing a hash of relevant
compile-time flags (`USE_NATIVE_128`, `USE_XGBOOST`, etc.). Engine
boot computes its OWN flag hash; mismatch → refuse-or-warn.

### Why this is interesting

- Closes the "trained on dev box without USE_NATIVE_128, deployed to
  prod with it" silent-drift class
- Mechanical enforcement vs operator discipline

### Why this is risky

- Flag hash needs to be the same definition on both sides; subtle
  changes to which flags are tracked = false positives
- Adding new flags to the tracking set requires re-stamping all
  models

### Suggested ship

**~3h, but design first:**

Define the canonical flag list. Probably: {USE_NATIVE_128,
USE_XGBOOST, build optimization level, maybe glibc version?}. Bake
into a constexpr at compile time, hash, embed.

## Idea 11: FPN-end-to-end for slow-path features (cross-build determinism)

**Origin:** 2026-05-02 v5.9.5 closure question — "if FPN reduces
drift, do we use it everywhere?" Answer: hot path yes, slow path
no. RollingStats / RegimeSignals math is in `double`; `Compute_*`
fns wrap the result via `FPN_FromDouble<F>` purely for typing
consistency (`FeatureRegistry.hpp:143-147`).

### What it would do

Convert RollingStats + RORRegressor + FlowFeatures to FPN-typed
math (mean / variance / correlation / slope / EMA / EWMA all in
fixed point). `Compute_*` fns then return native FPN values
without the `FromDouble` round-trip.

### Why this is interesting

- IEEE-754 double `+` is non-associative — `(a+b)+c ≠ a+(b+c)` for
  some values. Compiler optimization, FMA availability, SIMD vs
  scalar can reorder additions and produce slightly different
  results across builds.
- FPN integer math is fully associative — bytewise identical across
  any compiler / -O level / -march flag.
- Closes the "trainer compiled with -O2, engine compiled with -O3,
  feature distributions silently differ" class — orthogonal to
  cross-binary handshake (which CATCHES the mismatch but doesn't
  PREVENT it).
- Within same-build, v5.9.2 replay-determinism test already verifies
  bytewise identity, so this is purely for cross-build robustness.

### Why this is risky

- ~500 LOC of double math to convert; carries risk of off-by-one
  precision differences during refactor
- All existing models would need retraining (feature distributions
  shift slightly when math switches from float-add to FPN-add)
- FPN division is ~20ns vs double's ~3ns; only acceptable because
  RollingStats is slow-path
- FPN sin/cos for hour-of-day signals don't have first-class
  primitives — would need lookup-table or polynomial approx
- Risk that some `double`-typed external inputs (e.g. depth-book
  imbalance from float JSON) need explicit pinning

### Suggested ship

**~2-3 days; staged:**

1. Subship A: FPN versions of RollingStats primitives (mean,
   variance, slope) with snapshot tests vs current double values
   (epsilon-tolerance to confirm bounded difference).
2. Subship B: convert RegimeSignals computation; run replay-
   determinism test to verify same-build identity preserved.
3. Subship C: retrain reference models, document the
   `MODEL_FORMAT_VERSION` bump (this WOULD justify a format bump
   since the feature distribution shifts) and refusal-on-load for
   pre-v5.10 stamps.

Cross-check with `/parity-check features` before each subship.

### Lower-cost alternative

If full FPN conversion is too expensive: pin compiler flags into
the model fingerprint per Idea 10 (build_flags hash). That refuses
load on cross-build mismatch but doesn't enable safe
cross-build inference. Strictly weaker than FPN-end-to-end but ~3h
instead of ~2-3 days.
