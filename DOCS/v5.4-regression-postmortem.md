# v5.4 Regression Postmortem — strategy correctness + per-core slow-path data flow

Started 2026-04-29 evening. Living document — findings recorded as they
land during the investigation per `plans/2026-04-29-strategy-correctness-audit.md`.

This is the durable artifact. Plans go in `plans/` and rot; postmortems
live in `DOCS/` and get read by the next person doing an architectural
sprint that touches the same code paths.

## Executive summary

Post-v5.0 (per-core slow-path is the new default architecture), multiple
behaviors that worked under the legacy centralized arch are subtly
broken:

1. **Strategy trailing-SL/TP is dead-write across all 5 strategies.** Every `_ExitAdjust` writes `pos->stop_loss_price` / `pos->take_profit_price`. The hot path doesn't read those fields after entry — it reads `core->live_sl` and `core->live_tp` which are set once on entry. Result: trailing-SL feature is GUI-cosmetic only; positions actually run to entry-time SL regardless of how high price went.
2. **Display vs reality mismatch in Positions panel** (corollary of #1). Operator looking at the GUI sees the cosmetic SL value and forms wrong mental model about where actual exits will fire.
3. **Regime classifier appears stuck on RANGING** across all cores regardless of market conditions. Diagnostic A.2 will confirm whether the classifier inputs are zero (data flow broken) or whether classifier thresholds vs actual signal magnitudes don't match. Pending.
4. **Slow-path p99 regressed from ~200µs to ~1000µs** since v5.0. Steady-state is around 310µs (per the GUI breakdown). The 1000µs spikes are tail outliers — root cause not yet identified. Likely candidates: cache-miss pattern from per-engine 3MB heap-allocated slow_state, ema_price torn read between producer and per-core thread, or slow_state TLB pressure.
5. **Stale `(in pos)` flag on EMA + spacing-halt on multiple cores** — appears to be a cooldown-counter or last-entry-tick that isn't cleared on position close. Diagnostic A.4 pending.

These regressions all share a common architectural root: the v5.0 sprint
moved state from "implicitly shared across one slow-path thread" to
"explicitly per-core, owned by N slow-path threads." Implicit behaviors
the centralized path had didn't all transfer when the per-core paths
were written, because the centralized path's behavior wasn't
exhaustively documented before the split.

## Finding F1 — strategy `_ExitAdjust` writes are dead

**Severity:** feature-broken (trailing-SL/TP doesn't work). Not a safety
issue — the entry-time SL is still active, so positions DO have downside
protection. They just don't get the "lock in profit as price rises"
behavior that the trailing logic appears to provide.

**Where:**
- `Strategies/Momentum.hpp:298, 303, 312` — `pos->take_profit_price` / `pos->stop_loss_price` writes
- `Strategies/MeanReversion.hpp:511, 517, 526` — same pattern
- `Strategies/MLStrategy.hpp:151, 155, 162` — same pattern
- `Strategies/private/EmaCross.hpp:132, 151, 160` — same pattern
- `Strategies/RegimeDetector.hpp:690, 694, 700, 707, 712, 718, 722, 727` — regime-change handler writes

**Why dead:**
- `CoreFrameworks/ExecutionCore.hpp:268`: hot path reads `sl = active ? core->live_sl : core->cached_params.sg_stop_loss_price`
- `CoreFrameworks/ExecutionCore.hpp:417-425`: `core->live_sl` and `core->live_tp` are set ONCE on entry (in the entry-time branch of SG_Evaluate)
- No code path updates `core->live_sl` or `core->live_tp` after that initial set
- The only mechanism that DOES affect the hot path's effective SL post-entry is `pending_params.ratchet_sl`, pushed via seqlock by `EventLoop_TrailingSLRatchetOneCore` (line 2123+)

**What user sees:**
- GUI Positions panel reads `pos->stop_loss_price` and displays it
- Strategy `_ExitAdjust` updates `pos->stop_loss_price` cosmetically
- Operator sees what looks like a trailing SL but it has no effect on actual execution
- Position runs to its entry-time SL (set from `gate.sg_stop_loss_price`)

**Concrete example (from screenshot):** MOM long at $75848, GUI displays SL at $76032 (above entry). Position bleeds to $75694 (-0.20%). Operator wonders why SL didn't fire when price was below the displayed SL. Answer: actual hot-path SL is `core->live_sl ≈ $75664` (below entry, set at entry time). Position will fire SL at $75664, not $76032. The displayed SL is the ratcheted-up cosmetic value.

**Confirmation evidence:** grep across `Strategies/` shows zero writes
to `core->live_sl`, `core->live_tp`, or `pending_params.ratchet_sl`
from any strategy's `_ExitAdjust`. The single legitimate path to update
the hot-path SL post-entry (`EventLoop_TrailingSLRatchetOneCore`) lives
in `ControllerEventLoop.hpp`, is gated on `gain_pct >= cfg.tp_hold_score`,
and is the only writer to `pending_params.ratchet_sl` outside of
regime-change handler at line 1535.

**Why it likely worked pre-v5.0:** unconfirmed, but two hypotheses:
1. Legacy `PortfolioController` directly compares positions against
   `pos->stop_loss_price` / `pos->take_profit_price` (line 614+ has writes
   to these fields in the legacy path) — implying the legacy hot path read
   them per-tick. The sharded `ExecutionCore` cache-snapshots them at
   entry into `live_sl`/`live_tp` for hot-path speed.
2. The split into ExecutionCore was done for hot-path latency, but the
   strategy-side `_ExitAdjust` code wasn't migrated to use the new
   `pending_params.ratchet_sl` channel. Those `_ExitAdjust` functions
   compiled fine but became no-ops semantically.

**Fix direction (deferred — TBD which approach):**

A. **Strategies write to `pending_params.ratchet_sl`** (correct mechanism).
   Each `_ExitAdjust` calls a helper that writes the slow-path-pushable
   ratchet. v5.1.7 fee-floor cap applies automatically.
   - Pro: minimal hot-path change; uses the existing pipe.
   - Con: ratchet_sl is monotonic (max-only) — strategies that want to
     ratchet TP independently or tighten SL on regime change can't do
     it via ratchet alone.

B. **Add `live_sl`/`live_tp` update channel from slow path** (parallel
   to ratchet). Strategy `_ExitAdjust` writes go through a slow-path
   helper that updates `core->live_sl` directly via seqlock or atomic.
   - Pro: matches strategies' current intent (write the position's SL/TP)
   - Con: more channels = more state to keep consistent.

C. **Make hot path read `pos->stop_loss_price` per tick** (revert the
   v5.0 cache-snapshot). Loses the live_sl optimization but exactly
   matches the legacy behavior.
   - Pro: zero strategy code changes needed.
   - Con: per-tick load from Portfolio struct = cache miss potential
     in hot path. Latency regression. Probably wrong direction.

Most likely fix is **A** with strategies opting into the existing ratchet
channel. The dead `pos->stop_loss_price` writes get removed entirely as
the strategies stop writing them.

## Finding F2 — display/reality mismatch (corollary of F1)

**Severity:** UX confusion. Operator forms wrong mental model.

**Where:**
- GUI Positions panel reads `pos->stop_loss_price` for the SL column
- Hot path's actual SL comes from `core->live_sl` + `cached_params.ratchet_sl`

**What user sees:** strategy-side SL writes are visible (e.g., MOM
trailing-up the cosmetic SL above entry). But actual execution behaves
according to the entry-time SL (or the ratchet pushed by
`EventLoop_TrailingSLRatchetOneCore`). The two diverge.

**Fix direction:** when F1 is fixed (option A), strategies write to
ratchet which is what the GUI should also display. The display fix
follows the data-flow fix — make the GUI show the same field the
hot path uses.

## Finding F3 — regime stuck on RANGING (PENDING DIAGNOSTIC)

**Severity:** feature-broken. AUTO routes to RANGING-default (MR) and
never switches; DIP/EMA may have regime-aware filtering that's
similarly stuck.

**Diagnostic:** TT_REGIME_DEBUG=1 stderr trace added to
`Regime_Classify`. Logs every 16th cycle: `short_count`,
`ema_sma_spread`, `long_spread`, `r2`, `ror_slope`, `ror_ready`,
`vol_ratio`, `trending_score`, `volatile_score`, `detected`,
`current_regime`, `proposed_regime`, hysteresis state.

**Pending answers:**
- Does ema_sma_spread have non-zero values? (If always 0 → either
  ema_price is zero or rolling.price_avg is zero in per-core slow_state)
- Does ror_ready ever become 1? (If never → RORRegressor not warming up)
- Does trending_score ever reach 2? (If never → classifier rejects all
  signals; bug in score components)
- Does proposed_regime ever change? (If always 0 → classifier itself
  is the issue; not a hysteresis tuning problem)

**Hypothesis (pre-diagnostic):** ema_sma_spread is small because
ema_price is per-tick-fresh (replicated by producer thread) but
rolling_short.price_avg is per-cadence-stale (only updated by per-core
slow-path thread every 256 ticks). The two trails of price live at
different freshness levels. Their difference might be artificially
compressed.

## Finding F4 — slow-path p99 regressed 200µs → 1000µs (PENDING)

**Severity:** performance regression. Not a safety issue (slow path is
not on the critical path; cadence is every ~3 seconds with a 1ms cycle),
but indicates a hidden inefficiency or race.

**Steady-state breakdown** (from GUI in user's screenshot):
- Rolling: 325µs p50 (96% of cycle)
- Rebuild: 14µs p50
- Push: 123ns p50
- TimeExit + TrailSL: <1µs combined
- Σ p50: 340µs

**1000µs spikes:** tail-only. Steady is ~340µs, spikes go to ~1ms. The
delta of ~660µs is what we want to find. Per-section breakdown gating
on > 500µs would isolate which section spikes (Phase A.5 diagnostic).

**Hypotheses:**
- Cache pattern: per-engine 3MB heap-allocated slow_state means each
  engine's per-cadence access touches a different cache line cluster.
  Centralized arch had one thread accessing one slow_state — better
  cache residency. Per-core arch has 4 threads each touching their own
  3MB block — TLB pressure + L2/L3 thrashing.
- Cross-thread ema_price torn read: producer fans ema_price to all
  engines per-tick. FPN<F=64> = 4096 bits = 512 bytes. Per-core thread
  reads `sst->ema_price` during rebuild. Concurrent producer write +
  per-core read = data race. TSan would flag this. Torn read produces
  occasional stalls + corrupted regime inputs.
- Snapshot save fired during slow-path cadence. Rare but possible
  contention. Phase A.5 diagnostic stderr trace will catch this.

## Finding F5 — stale `(in pos)` flag + spacing halts (PENDING DIAGNOSTIC)

**Severity:** silent strategy lockout. EMA had one losing trade and
hasn't been able to take a position since. Spacing halts other cores
that haven't traded recently.

**Pending diagnostic:** Phase A.4 — log every site that writes/clears
`last_entry_tick`, `last_exit_tick`, or any cooldown-style field on
CoreContext.

**Hypothesis:** `last_entry_tick` (or similar) is set on entry but not
cleared on position close. The "spacing" gate uses this to enforce
minimum N ticks between trades. If the field stays non-zero
indefinitely after close, spacing gate stays armed forever for that
core. After the ONE losing trade, EMA's last_entry_tick = some_tick;
no clear-on-close path; spacing gate halts all subsequent entries.

## Finding F7 — Strategy `_Adapt` orphaned in sharded path (CRITICAL)

**Severity:** systemic. Every strategy's per-cadence state adaptation is dead in the sharded engine.

**Where:**
- `Strategies/Momentum.hpp:90` `Momentum_Adapt`
- `Strategies/MeanReversion.hpp:123` `MeanReversion_Adapt`
- `Strategies/SimpleDip.hpp:43` `SimpleDip_Adapt`
- `Strategies/private/EmaCross.hpp:45` `EmaCross_Adapt`
- `Strategies/MLStrategy.hpp:64` `MLStrategy_Adapt`

All five exist as functions; all five are called ONLY from `CoreFrameworks/PortfolioController.hpp` (the legacy single_core path). The sharded engine (`ControllerEventLoop.hpp`, `EngineSharded.hpp`, `ShardedBacktestDriver.hpp`) never calls any `_Adapt` function.

**What this means:** strategies have no per-cadence memory in the sharded engine. State-based behaviors that the strategy authors wrote — Momentum's volume-confirmation tracking, MR's trend-exhaustion detection, MLStrategy's prediction smoothing — are completely absent at runtime.

**Confirmation:** filtered grep across all sharded-path files for `(Momentum|MeanReversion|SimpleDip|EmaCross|MLStrategy)_<fn>(` shows only `_BuildParameters` variants. No `_Init`, `_Adapt`, `_BuySignal`, `_ExitAdjust` calls.

## Finding F8 — Strategy state structs not allocated per-core

**Severity:** corollary of F7. Even if `_Adapt` were called, there's no place to store the state.

**Where:**
- `Strategies/Momentum.hpp:40` `MomentumState<F>` — never instantiated in sharded `CoreContext`
- `Strategies/MeanReversion.hpp:45` `MeanReversionState<F>` — never instantiated
- `Strategies/SimpleDip.hpp:23` `SimpleDipState<F>` — never instantiated
- `Strategies/private/EmaCross.hpp` `EmaCrossState<F>` — never instantiated
- `Strategies/MLStrategy.hpp:28` `MLStrategyState<F>` — never instantiated

`PortfolioController` allocates these as members (`ctrl->mean_rev`, `ctrl->momentum`, etc.). `CoreContext` in `ControllerEventLoop.hpp` does not. Adding `_Adapt` calls without first allocating state would crash on null deref.

## Finding F9 — `Regime_AdjustPositions` orphaned in sharded path

**Severity:** regime-transition-aware position management is dead.

**Where:** `Strategies/RegimeDetector.hpp:665` `Regime_AdjustPositions` — called only from `PortfolioController.hpp:1656/1683/1858`. Never called in sharded.

**What this does (or rather, would do):** when regime transitions (RANGING→TRENDING, TRENDING→VOLATILE, etc.), open positions get their TP/SL widened or tightened to match the new regime's risk profile. In sharded, regime transitions don't trigger any position adjustment. Positions opened in RANGING regime keep their RANGING-tuned TP/SL even if the market shifts to VOLATILE.

(The smaller regime-change ratchet at `ControllerEventLoop.hpp:1535-1551` only writes `pending_params.ratchet_sl` for the position's SL ratchet — it doesn't widen TP or do the regime-specific adjustments `Regime_AdjustPositions` does.)

## Finding F10 — Strategy `_ExitAdjust` orphaned in sharded path

**Severity:** confirms F1 — trailing-SL/TP across all five strategies is silently no-op AT TWO levels:
1. Even if `_ExitAdjust` ran, its writes are dead (F1 — hot path doesn't read `pos->stop_loss_price`)
2. `_ExitAdjust` doesn't even run in the sharded path

**Where:**
- `Strategies/Momentum.hpp:265` `Momentum_ExitAdjust`
- `Strategies/MeanReversion.hpp:457` `MeanReversion_ExitAdjust`
- `Strategies/private/EmaCross.hpp:122` `EmaCross_ExitAdjust`
- `Strategies/MLStrategy.hpp:130` `MLStrategy_ExitAdjust`

(SimpleDip doesn't have `_ExitAdjust` — it's the simplest strategy.)

All called only from `PortfolioController.hpp`. Never called in sharded.

So the displayed-SL-above-entry behavior the user observed (image 7: SL at $76032 above entry $75848) cannot come from `Momentum_ExitAdjust` because that function never runs. It must come from initial position-open setup or from the smaller regime-change ratchet path (`ControllerEventLoop.hpp:1535`). Worth confirming separately.

## Architectural shape of the regression — full picture

The legacy `PortfolioController` had a five-stage strategy lifecycle:

```
INIT  → MeanReversion_Init / Momentum_Init / etc. — at engine start
ADAPT → ..._Adapt — per cadence, updates strategy state
SIGNAL → ..._BuySignal — per cadence, reads state, emits BuySideGateConditions
ENTRY → BG checks BuySideGateConditions, fires entry
EXIT  → ..._ExitAdjust — per cadence on open positions, trails SL/TP
       Regime_AdjustPositions — per regime transition, widens/tightens
```

The sharded engine implemented ONLY:

```
BUILD → ..._BuildParameters — per cadence, recomputes from rolling stats only
ENTRY → BG checks GateParameters, fires entry
        (initial TP/SL from BuildParameters' sg_take_profit_price / sg_stop_loss_price)
RATCHET → EventLoop_TrailingSLRatchetOneCore — per cadence, writes pending_params.ratchet_sl
            (single mechanism, not strategy-specific; only affects SL never TP)
```

Everything between INIT and EXIT was supposed to be subsumed by `_BuildParameters`, but that function takes only `(rolling, config, allocated_balance, out)` — no strategy state, no exit handling, no regime transitions. The strategy authors' state-driven logic exists in the codebase but doesn't run.

## Lessons codified for future architectural sprints

When migrating between architectures (legacy ↔ new, single-thread ↔ per-core, etc.):

1. **Enumerate every public function of the migrating module BEFORE coding the new arch.** Make a checklist. For each function: where is it called in the OLD arch? Where will it be called in the NEW arch? If "nowhere" — is that intentional? Document the reason.

2. **The "calls graph diff" check.** After the migration: `comm` between functions called in the legacy entrypoint vs functions called in the new entrypoint. Anything in the legacy-only set should be reviewed. (We just used this technique to find F7-F10.)

3. **Don't trust `_BuildParameters`-style refactors that "subsume" multiple functions.** If a new function claims to subsume legacy functions A, B, C, write a parity test: feed legacy A+B+C the same input as new function, assert outputs match.

4. **Strategy interface contract should be a single-page document.** Currently the five-stage lifecycle (Init/Adapt/BuySignal/BuildParameters/ExitAdjust) exists implicitly across the codebase. Write it down explicitly in `DOCS/CLAUDE_INVARIANTS.md`. Each architecture must implement all stages or explicitly mark stages "skipped — reason."

## Finding F6 — `regime_state` per-core, but regime is a market signal (ARCHITECTURAL)

**Severity:** wasted CPU + state divergence risk. Not a current bug
(yet) but a foundation for future bugs.

**Where:** `state->cores[c].regime_state` — one RegimeState per engine.
Each AUTO core independently runs `Regime_ComputeSignals` →
`Regime_Classify` per cadence.

**Problem:**
- All 4 cores trade BTCUSDT — same instrument, same market
- All 4 should converge to the same regime classification
- Per-core duplication means 4× the work for the same answer
- Each core has its own `hysteresis_count` — cores can transiently
  disagree on the regime even though the market has one truth state

**Fix direction:** centralize regime computation in producer thread
(matches `ema_price` pattern from v5.1.0); replicate the classified
regime int to each engine's CoreContext. AUTO cores read the shared
regime, route via REGIME_STRATEGY_TABLE.

This is `plans/2026-04-29-strategy-correctness-audit.md` Phase C.6.

## Architectural pattern that caused the regressions

Common thread across F1-F6: the v5.0 sprint moved state from "shared
across one thread" to "explicit per-core" without exhaustively
documenting what the centralized arch was doing IMPLICITLY. The
per-core code was written to handle the explicit cases; the implicit
ones (pos field updates, regime-as-shared-signal, cooldown-as-per-core,
ema-price-freshness) lost their behavior in the migration.

**Lessons for future architectural sprints:**

1. **Before splitting shared state, exhaustively enumerate all writers
   and readers.** Both code paths AND mental models. For each, document
   how the shared version's behavior is preserved in the split.

2. **Greps as gates.** `grep "pos->stop_loss_price"` across the entire
   codebase — every writer is a candidate dead-write after a hot-path
   redesign that introduces a cache snapshot. Make this a pre-merge
   readiness check.

3. **Display vs execution divergence is invisible.** When the GUI reads
   field X but execution reads field Y, the operator sees X looking
   correct while Y silently drifts. UI/execution should read the same
   source. If they MUST be different (latency reasons), the divergence
   should be documented as an invariant.

4. **Per-core duplication of market signals is wasteful.** Anything that
   describes the market (regime, volatility class, large-trade flag)
   should be computed once per producer pass and replicated to engines.
   Strategy-level signals (gate parameters, ML predictions, position
   sizing) are correctly per-core.

5. **A/B test EVERY architectural sprint.** Pre-v5.0 vs post-v5.0 should
   produce identical training data on identical input. The
   `parity_harness` test catches feature drift but not behavioral drift
   — extend it.

## Prevention going forward

These should land in v5.4.0 or earlier (per the audit plan Phase D):

- **INVARIANTS_MAP entry: "Hot path SL/TP source of truth"** — explicit
  documentation that SG_Evaluate reads `core->live_sl + cached_params.ratchet_sl`
  and ANY code path attempting to update the active SL must write
  ratchet_sl, not pos->stop_loss_price.

- **Compile-time / test-time check: dead-write detector.** Test that
  flexes each strategy's _ExitAdjust against a known position state,
  asserts pos->stop_loss_price changes (cosmetic write happens), then
  verifies the hot-path effective_sl ALSO changes (via ratchet_sl).
  If only the cosmetic field changes, FAIL — strategy writes are dead.

- **Readiness skill check: split-state migration.** When a plan moves
  shared state to per-core, require enumeration of (a) all current
  readers, (b) all current writers, (c) the per-core equivalent of
  each, (d) test that legacy + per-core paths produce identical
  output on identical input.

- **Health log infrastructure** (`MemHeaders/HealthLog.hpp`, written this
  session): always-available structured diagnostic output, gated on
  cfg, persisted across runs. Replaces ad-hoc env-gated stderr traces.
  Future regressions can be diagnosed without code changes; just enable
  the cfg.

- **Display invariant check.** GUI panels showing "live" trade state
  should read the same field the execution path uses. INVARIANTS_MAP
  entry; readiness skill check on plans that touch GUI state display.
