# v4.7.19 — Counter/CSV Atomicity + Double-Close Guard

**Date:** 2026-04-27
**Branch:** `experiment/per-core-sharding`
**Status:** experiment branch
**Prerequisite:** v4.7.18
**Severity:** real-money / accounting-correctness — must land before live trading
**Rollback tag:** `pre-v4.7.19-counter-fix`

## Summary

Architectural fix for an accounting class of bug where heartbeat counters, fees, and realized P&L could drift from the actual fill record. Surfaced as `Stats: exits: 2 (7 fills)` while the trade log CSV held only 5 exit rows. The 2-row discrepancy was the visible symptom of a deeper rule violation: counter bumps and CSV writes were at decoupled call sites that could fire independently.

## Root cause

Heartbeat counter bumps fired in **four** different call sites:

1. `EventLoop_OnEvent` mode-1 branch (every drained TradeEvent)
2. `EngineSharded.hpp` manual-close lambda (every Close-button click)
3. `EventLoop_TimeExit` shared helper (every force-close on max_hold_ticks)
4. (`OrderManager_HandleFill` did NOT bump — only wrote the CSV)

CSV writes only fire from #4. So any failure path between `Submit` and `HandleFill` leaves the counter bumped without a CSV row:

- `OrderManager_Submit` returns 0 when the order table is full
- `result_queue.TryPush` fails when the result ring is full (paper mode)
- `Submit` succeeds but the SELL targets an already-closed slot, so `HandleFill` should reject — but the rejection path was missing

In addition, `Portfolio_CloseSlot` did NOT zero `entry_price` or `quantity` on close — it only cleared the bitmap bit. A duplicate SELL fill (manual-close racing with hot-path SG, or a stale event drained after `HandleFill` had already run) would read the stale fields and:

- compute a phantom `gross = (current_price - stale_entry) * stale_qty`
- charge a real `exit_fee` against `balance`
- write a phantom CSV row with the stale entry_price + current exit_price
- bump `total_filled`, `taker_fills_count`, `total_taker_fees`
- populate `last_closed_mask`, triggering `DrainPostFill` to drain phantom CoreContext stats

In paper mode this drains a few cents to a few dollars per ghost fill from balance + drifts every per-core stat. In live mode the duplicate `Submit` reaches Binance and either fills as an unintended SHORT or gets rejected — both bad for real money.

## Fix

**Single source of truth: `EventLoop_DrainPostFill`.**

`HandleFill` populates `oms->last_opened_mask` / `oms->last_closed_mask` exactly when a real fill mutates the portfolio + writes a CSV row. `DrainPostFill` walks those masks and was already updating per-core CoreContext stats. v4.7.19 moves the heartbeat counter bumps into the same loop:

```cpp
// inside DrainPostFill, entries loop
ctx.entries_processed++;
state->total_entries++;
state->total_events_processed++;

// inside DrainPostFill, exits loop
ctx.exits_processed++;
state->total_exits++;
state->total_events_processed++;
```

Counter and CSV write are now atomic with respect to the actual fill. They cannot drift.

The decoupled bump sites are removed:

- `OnEvent` mode-1 branch returns without bumping
- Manual-close lambda removes its bump (Submit → HandleFill → DrainPostFill picks it up)
- `EventLoop_TimeExit` removes its bump (same flow)

**Double-close guard in `HandleFill` SELL branch:**

```cpp
if ((oms->portfolio.active_bitmap & (uint16_t)(1u << pslot)) == 0) {
    fprintf(stderr, "[OMS] HandleFill: SELL on closed slot — no-op\n");
    return;
}
```

Stops phantom fees, ghost CSV rows, and unintended live SHORTs at the root.

## Display cleanup (rolled in)

- **Trade history `St` column**: removed redundant `.B` suffix on leg-B exits — the v4.7.18 `Leg` column already conveys it.
- **Trade history reason logic**: tolerance-based FLAT band (`|exit - entry| < entry × 0.5bps`) so legitimate near-flat exits and any residual rounding don't spuriously read as "SL".

Note on FPN precision: FPN<64> is exact (64 fractional bits). The CSV writes prices at `%.8f`. The reason logic operates on parsed doubles that preserve sub-cent precision — strict `<` / `>` comparisons correctly classify sub-dollar moves. The tolerance fix is purely for cosmetic noise-floor classification, not a precision workaround.
