# 2026-04-09 — v3.9.0-experiment: OMS Phase 03 (Order Event Log + Portfolio Fold)

scope: experimental branch `experiment/per-core-sharding`. follow-on to the
OMS phase 01+02 commit at `pre-oms-phase-03` tag. lifts the portfolio from
directly-mutated state to a derived view that can be reconstructed from
an append-only order event log. dual-mode: legacy OnEvent path stays as
the default, new event-log path is gated behind `oms_event_log_mode=1`.

## Shared

- `ControllerConfig.hpp`: new `oms_event_log_mode` field (0=legacy, 1=event_log,
  default 0). parser accepts both string ("legacy"/"event_log") and int.
- `Limits.hpp`: no changes (MAX_INFLIGHT_ORDERS and MAX_BINANCE_WORKERS from phase 02 still in place).

## Execution Engine

### state migration (chunks 1A + 1B)

all financial state moved from `EventLoopState` to `OrderManagerState`:
portfolio, balance, realized_pnl, fee_rate, kill switch thresholds +
peak + tripped flag + trips count, trade_log pointer. EventLoopState
is now a thin dispatcher with cores[], registered_count, event counters,
and an `OrderManagerState<F>* oms` back-pointer.

11 forwarding accessor functions added to ControllerEventLoop.hpp
(EventLoopState_Balance, _RealizedPnl, _FeeRate, _Portfolio, _PortfolioMut,
_KsMinBalance, _KsMaxDrawdownPct, _KsPeakBalance, _KillSwitchTripped,
_KsTripsTotal, _TradeLog) so existing call sites have a migration path.

EventLoopState_Init takes `(state, oms_pointer)` instead of
`(state, starting_balance, fee_rate)`. EventLoopState_InitLegacy
convenience helper wraps both for tests.

OrderManager_Init takes starting_balance + fee_rate as new params
(6 args total, was 3 in phase 02). the OMS is now self-contained
from init onwards.

17 files updated in the migration (5 core headers + 12 test/bench files).

### order event log (chunk 2)

new `CoreFrameworks/OrderEventLog.hpp`:
- `OrderEvent<F>` struct: self-contained (order_id, timestamp, event type,
  order type BUY/SELL, core_id, fill price, fill qty, intended TP/SL,
  short reason string). no external lookups needed for replay.
- `OrderEventLog<F>`: growable buffer (malloc + 2x realloc), initial
  capacity 16384 events (~2 MB). append-only, monotonic event_ids.
- `OrderEvent_MakeFill` / `OrderEvent_MakeRejection` convenience builders.
- `Portfolio_FromEventLog<F>`: deterministic fold function. walks events,
  replays every FULL_FILL, produces a `FoldResult<F>` with balance (FPN<F>,
  not double), realized P&L, portfolio state, fill count. same fee model
  as OnEvent. FPN arithmetic throughout for exact head-to-head comparison.

### event_log_mode behavioral split (chunk 3)

`EventLoop_OnEvent` gates on `oms->event_log_mode`:
- mode 0 (legacy, default): unchanged. OnEvent mutates portfolio + balance
  directly, same as every commit before phase 03.
- mode 1 (event log): OnEvent just bumps counters (entries_processed,
  exits_processed, total_events_processed). the actual portfolio mutation,
  balance update, kill switch peak tracking, and event log append happen
  inside `OrderManager_Tick` when the CMD_FILL_RESULT arrives.

Order struct gained context fields (intended_tp, intended_sl, event_price,
strategy_id) so the OMS fill handler is self-contained at fill time.

mode 1 paper path: instead of the old short-circuit, mode 1 paper
allocates a real OMS slot and pushes a synthetic CMD_FILL_RESULT with
event_price as the fill price. OMS_Tick processes it through the same
fill handler as live mode.

### backtest wiring (chunk 4)

ShardedBacktestDriver gains an `OrderManagerState<F>* oms` field (default
nullptr, backward-compatible). RunTick and Run call `OrderManager_Tick`
after each `EventLoop_DrainEvents`. BacktestSharded.hpp passes the
already-constructed OMS pointer to the driver.

### head-to-head acceptance test (chunk 5)

`test_event_log_head_to_head.cpp`: runs 2000-tick synthetic stream through
both mode 0 and mode 1. **27 assertions, 0 failures. byte-identical
balance across 54 entries and 52 exits.** event log fold cross-check
also matches exactly. mode 1 determinism test (run twice) passes.

## Known limitations

- **mode 1 through ShardedBacktestDriver requires a DrainEventsWithOMS
  helper** (open-coded drain that calls OrderManager_Submit after OnEvent).
  the standard EventLoop_DrainEvents doesnt call Submit, so mode 1
  portfolio stays empty through the driver. the head-to-head test
  implements its own drain. if mode 1 is ever used through the standard
  driver API, the driver needs the same integration bridge.
- **trade log CSV in mode 1**: wired in commit 7ba92ca (post-phase-03).
  the fill handler now calls ShardedTradeLog_RecordEntry/Exit.
- **partial fills still deferred to phase 06.**
- **rejection reset path still TODO** — executor stays in optimistic
  state after a failed order.

## Audit findings (2026-04-09)

full code audit of all 13 OMS files after phase 03 shipped. 5 targeted
sub-audits (exit qty flow, fee parity, header deps, migration completeness,
kill switch parity). rollback tag: `pre-oms-audit` at c842b24.

**4 bugs found (none structural):**

1. **`submitted_at_us` never set** — `Order_Init` zeros it, `Submit` never
   writes it. all event log + trade log timestamps are 0 in mode 1.
   (`Order.hpp:119`, `OrderManager.hpp:350-356`)

2. **no bounds check on `core_id` in mode 1 fill handler** — `(int)o->core_id`
   used as portfolio slot index without guard. currently safe from the
   drainer, but the fill handler has no local check.
   (`OrderManager.hpp:489`, `:507`)

3. **trailing drain at shutdown uses wrong drain for mode 1** —
   `EventLoop_DrainEvents` (no Submit) in the post-producer trailing drain.
   late events in mode 1 get counter bumps but no portfolio mutation.
   (`EngineSharded.hpp:569-573`)

4. **producer/drainer race on `oms->balance`** — producer reads via
   `KillSwitchEvaluate`, drainer writes via fill handler. FPN<64> is 64
   words, torn reads possible. pre-existing (not OMS-specific).
   (`EngineSharded.hpp:408`, `OrderManager.hpp:516`)

**verified clean:**
- exit qty flow correct (no mismatch between drainer snapshot and fill handler)
- fee model byte-identical across mode 0, mode 1, and fold
- header dependency graph acyclic (5-layer, no cycles)
- direct field access migration 100% complete (zero legacy state.balance etc.)
- kill switch parity identical between modes (race is pre-existing)
