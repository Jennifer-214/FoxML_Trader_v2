# 2026-04-25 (very late evening) — v4.0.2: live-trading polish round

Three more commits on top of v4.0.1 surfaced during continued live testing.
Pre-existing bugs that hadn't been hit before because nobody had run the
engine in this exact configuration with this much scrutiny.

## What got fixed

### TickRecorder timestamp units (4f61303) — load-bearing for ML training

`TickRecorder_DateInt` divided microseconds by **1000** instead of
**1,000,000**. Result: every recorded tick file had a year derived from a
time_t that was 1000× too large, producing filenames like
`58286-05-16.csv` instead of `2026-04-25.csv`. Worse, the recorder thought
every single tick was a new "day" (because the millisecond-treated
microsecond value increases rapidly), so it created one new file per tick
— burning through hundreds of fake-date files within seconds of starting.

DepthRecorder uses the correct `/1e6` divisor — that's why depth files
correctly named `data/BTCUSDT/depth/2026-04-26.csv` while tick files were
`data/BTCUSDT/58286-05-16.csv` simultaneously.

**Why this matters for ML:** any ML model trained on backtest data that
included these mis-named files was reading the same actual ticks but
labeled with corrupted dates. Since `BacktestData_Load` doesn't care
about filename — just file contents — the data itself was fine, but
file ordering during the post-pass label loop was scrambled (alphabetic
sort puts `2026-*` first, then `58286-*` last, even though the timestamps
inside both file ranges overlap).

After this fix, new tick recordings go to correctly-dated files. Old
fake-date files (`58286-*`) should be manually moved or deleted; their
contents are valid but their filenames misrepresent the actual recording
window.

### Warmup gating too aggressive (4f61303) — explained the "always 2 positions" bug

Pre-fix: `if (rolling.count >= 1) ExecutionCore_SetPermission(core, 1)`.

After the second tick, ALL cores got permission to trade. With 4 cores
running mixed strategies (e.g., MR for buy-below-avg, MOM for buy-above-avg),
exactly one of them ALWAYS fires on the next price tick — because price
is mathematically either > avg or < avg. With both armed, both classes
of strategies effectively race to be first.

Result every restart: instant 2 positions opened with garbage TP/SL
(rolling.price_avg + price_stddev hadn't stabilized at 1 sample of data,
so momentum's stddev-mult sizing produced near-zero TP/SL distances).

Fix: `cfg.min_warmup_samples` (defaults to 64 = half the short window)
is required before granting permission. 64 samples gives enough
rolling-stats stability for the gate-direction race to settle and for
strategy-specific sizing to compute non-trivial values.

Existing behavior preserved when `cfg.min_warmup_samples` is explicitly
set to 1 (degenerate fast-warmup mode for tests).

### Shutdown stage logging (4f61303)

Added per-stage "[sharded]   joining producer..." / "joining drainer..." /
"joining GUI..." / "closing recorders..." / etc. messages so when the
process refuses to exit cleanly, the last printed message tells us WHICH
thread is hung. Also reordered shutdown so depth thread (which has its
own `quit_requested` flag) gets signaled FIRST, before producer.join() —
caught a case where producer was waiting on the engine's general flag
but depth was still spinning.

### Cfg file protection (28d5fd7)

`engine.cfg`, `controller.cfg`, `backtest.cfg` now gitignored. Per-core
overrides + tuned values can no longer leak to the public repo by
accident. `build.sh` auto-seeds `engine.cfg` from `engine.cfg.example`
on a fresh clone so new devs have a working config.

### Barrier % input precision (922d21e)

Foxml_suite's TP/SL Barrier % inputs were clamped at 0.1 (one decimal +
0.1 step). At BTC tick scale with ~1k-tick lookahead, 0.1%+ barriers
hit so rarely that 99%+ of samples land in "stable" (the GUI's diagnosis
flagged this with "extreme imbalance"). Bumped to 3 decimals + 0.01
step so users can dial in 5-bp barriers (0.050) that produce balanced
multiclass labels.
