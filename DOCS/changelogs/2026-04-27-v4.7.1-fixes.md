**Date:** 2026-04-27
**Branch:** `experiment/per-core-sharding`
**Status:** experiment branch — under testing

## Summary

Cleanup pass after v4.7.0 shipped the partials scaffolding without the
runtime path actually working. Live engine_gui testing surfaced that
under partials:

- The Positions panel showed a Budget % of 200% on cores with open
  positions — meaning `core_open_notional` exceeded `allocated_balance`.
  The Phase 2.2 budget-clamp existed but wasn't firing.
- Trade history showed only one exit row per closed trade, no leg-A /
  leg-B staggering at different prices.
- Restarting the engine restored "phantom" positions that couldn't be
  exited — the panel showed 4-6 open positions but the hot path's
  SG_Evaluate never fired SELL events for them.

Three independent root causes, all addressed in this release.

## Root cause 1 — Mode-0 OMS fundamentally incompatible with partials

`oms_event_log_mode=0` (the v4.7.0 default — described in the cfg
comment as "legacy OnEvent path") had `EventLoop_OnEvent` doing the
portfolio mutation directly using `event.core_id` as the portfolio
slot. Both legs of a paired entry emit events with the SAME
`event.core_id` (the core, not the slot). Result:

- Leg A entry: `Portfolio_OpenSlot(slot=core_id)` opens slot N
- Leg B entry: `Portfolio_OpenSlot(slot=core_id)` opens slot N AGAIN —
  clobbers leg A
- AND `core_open_notional += FPN_Mul(price, intended_qty)` fires once
  per leg event with the FULL `intended_qty` — accumulates to 2× alloc
  → Budget 200%

Mode 1 (`event_log_mode=1`) was scaffolded as the design target where
OMS owns portfolio mutation and the drainer pattern handles partials
correctly via `portfolio_slot=2c+leg`. But mode 1 was incomplete —
`EventLoop_OnEvent`'s mode-1 branch only bumped counters; it never
updated `core_open_notional`, `core_realized`, `core_fees`, or
`core_wins`/`core_losses`. Flipping the default would have broken the
per-core panel display AND the per-core kill switch (which reads
`core_realized` to compute drawdown — would've stayed at zero, never
tripping).

### Fix: complete mode 1, then flip default

Two commits:

**`53624d9` — OMS-side per-fill bookkeeping:**
- New `OrderManagerState::FillRecord` (per-slot array, mirrors the
  existing `last_realized_return[]` pattern):
  - entry: `entry_notional` + `entry_fee`
  - exit:  `exit_net_pnl` + `exit_entry_notional` + `exit_total_fees`
           + `was_win`
- New `last_opened_mask` (separate from `last_closed_mask` so paired
  entry+exit on different slots in the same drain cycle don't lose data).
- `OrderManager_HandleFill` populates these on every BUY/SELL fill.
- `partial_exit_enabled` mirrored from cfg to OMS at sharded init.
- Pure data capture — nothing consumes it yet, no behavior change.

**`ad6ea0c` — Mode 1 default + drainer consumer:**
- New `EventLoop_DrainPostFill<F>(state, oms, sl_cooldown_cycles)` in
  `ControllerEventLoop.hpp`. Consumes `last_opened_mask` /
  `last_closed_mask` + `last_fill[]`. Runs on the drainer thread after
  every `OrderManager_Tick`. Maps slot → core_id via partials geometry
  (slot/2 with partials, slot otherwise). Both legs of a paired trade
  route their stats to the SAME `CoreContext` — partials only split
  the exit schedule, not the allocation.
- Updates: `core_open_notional` (entry +=, exit -=),
  `core_realized` (exit +=), `core_fees` (entry + exit),
  `core_wins`/`core_losses` (by `was_win`),
  `ConfidenceScorer_Update` (ML cores), SL cooldown,
  `pnl_feeder` push.
- The slot < `registered_count` bound check the legacy
  `drain_confidence_feedback` lambda used was wrong under partials
  (legB slots ≥ N silently skipped). Now uses `partial_on ? N*2 : N`.
- `cfg.oms_event_log_mode` default flipped 0 → 1.
- Hot path untouched (slow-path drainer thread only).

14 new test assertions: open_notional sums to alloc (no 200% bug),
core_realized accumulates on paired exits, both legs decrement
notional to ~0 after close, core_wins/losses count both legs,
partials-off regression preserved.

## Root cause 2 — Snapshot layout assumes single geometry

`SHARDED_SNAPSHOT_VERSION=2` persisted `portfolio.active_bitmap` +
`positions[]` but encoded NO indication of which slot-geometry was
active when saved. So a snapshot taken with `partial_exit_enabled=0`
yesterday (slots 0..3 = one position per core under 1:1 mapping)
loaded today with `partial_exit_enabled=1` was reinterpreted as paired-
leg geometry — slots 0..3 became "core 0 leg A, core 0 leg B, core 1
leg A, core 1 leg B". Strategy ID display was wrong (panel reads
`per_core[slot]` but slot now means leg, not core), and the hot path
treated four positions as two paired pairs.

### Fix: snapshot v3 with geometry byte

**`aaa9b41` — snapshot v3 partials-aware:**
- `SHARDED_SNAPSHOT_VERSION` 2 → 3.
- Header gains `partial_exit_enabled` byte + 3-byte pad.
- `ShardedSnapshot_Save<F>(state, path, partial_exit_enabled)` and
  `ShardedSnapshot_Load<F>(state, path, partial_exit_enabled)`
  signatures gain the cfg-state arg.
- Loader refuses files where saved-state ≠ current-cfg with explicit
  message: "written with partial_exit_enabled=N, current cfg=M —
  refusing load (slot geometry differs; restoring would create zombie
  positions). Starting fresh."
- Post-load `ExecutionCore` re-activation also gains slot/2 mapping
  so leg-B slots ≥ `registered_count` populate the leg-B mirror set
  (`active_b` / `entry_price_b` / `live_tp_b` / `live_sl_b`) instead of
  being silently skipped by the old `slot >= registered_count` bound
  check.
- Leg-B mirrors are NOT separately persisted — they're derived at
  load time from `portfolio.positions[2c+1]` (already in the existing
  OMS block). One source of truth, less to keep in sync.
- 5 new test assertions covering toggle-mismatch refuse + same-flag
  acceptance.

## Root cause 3 — Per-core kill switch fires silently

The Phase 3 per-core kill switch infrastructure (MTM peak/drawdown
tracking, trip on `dd_pct > threshold && drop > min_kill_loss`,
`zero_gate(9)` HALT_CORE_KILL on entries, snapshot persistence) was
fully wired since v4.0. Two `NotifyKind` enum entries were even
pre-allocated: `NK_CORE_KILL_TRIP=10` and `NK_CORE_BUDGET_EXHAUST=11`.
But the trip site at `ControllerEventLoop.hpp:1170` only `fprintf`'d
to stderr — no `Notify_Send`. A killed core fired silently as far
as the operator was concerned, AND the per-core panel didn't
visually mark a killed core's row.

### Fix: 2A — wire alerts + GUI surfacing

**`210aae0` — per-core kill switch alerts + GUI:**
- Trip site emits `Notify_Send(NOTIFY_ALERT, NK_CORE_KILL_TRIP, ...)`
  alongside the existing `fprintf`. Per-kind cooldown collapses storm
  trips to one alert per window. `g_notify` guard preserves backtest
  no-op semantics.
- Per-core P&L table tints killed-core rows red (subtle background),
  appends "!" to the core ID column, dims the strategy name (alpha
  0.45). Tooltip on Core ID shows dd% and "halted until manual reset".
- No changes to trip semantics — just makes existing safety visible.
