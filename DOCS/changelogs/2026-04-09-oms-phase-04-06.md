## Execution Engine

### phase 06A — idempotency keys (prerequisite)

`DataStream/BinanceOrderAPI.hpp`:
- `BinanceOrderAPI_MarketBuy/Sell` gained a `uint64_t client_order_id`
  parameter (default 0). when non-zero, appends `newClientOrderId=oms_<id>`
  to the POST body. prevents duplicate fills on network-timeout retries.

`CoreFrameworks/BinanceAdapter.hpp`:
- worker loop passes `p.client_id` through to the API call.

### phase 04 — user data websocket fill stream

new `DataStream/BinanceUserData.hpp` (~340 LOC):
- `BinanceUserDataState` struct with its own `BinanceOrderAPI` instance
  (per-thread, not shared with adapter workers), WSS connection state,
  listen key, two threads (WS + keepalive).
- WS thread: obtains listen key via `POST /api/v3/userDataStream` (API-key
  header only, no HMAC), connects WSS to `/ws/<listenKey>`, reads frames,
  parses `executionReport` JSON, pushes `CMD_WS_FILL` to `ws_result_queue`.
  on disconnect: sleep, re-obtain key, reconnect.
- keepalive thread: PUTs `/api/v3/userDataStream` every 25 minutes.
- `ud_parse_execution_report`: extracts `clientOrderId` ("c" → parse
  `oms_<id>`), fill price ("L"), fill qty ("l"), exchange orderId ("i"),
  execution type ("x" == "TRADE"). builds a `Command` for the SPSC ring.
- SSL/WebSocket plumbing duplicated from `BinanceCrypto.hpp` with `ud_`
  prefix (same patterns, different struct).

`CoreFrameworks/OrderManager.hpp`:
- `CMD_WS_FILL = 1` added to `CommandType` enum.
- `ws_result_queue` SPSC ring added to `OrderManagerState` (second ring,
  separate from REST `result_queue`). initialized in `OrderManager_Init`.
- `OrderManager_Tick` drains `ws_result_queue` after the REST queue.
  dedup: if order is already `ORDER_FILLED` (REST beat WS), skip silently.
  surprise fills (order_id == 0, no clientOrderId): logged, skipped,
  left for reconciliation.
- ACK-only handling: when REST result has `fill_qty == 0` and
  `avg_fill_price == 0`, order transitions to `ORDER_ACKNOWLEDGED` instead
  of `ORDER_FILLED`. slot stays open for WS fill.

`CoreFrameworks/BinanceAdapter.hpp`:
- `ws_active` atomic flag on `BinanceAdapterState`. when set, the worker
  loop's callback sends ACK-only (exchange_id populated, no fill data).
  when cleared, existing phase-02 full-fill behavior is preserved.

`CoreFrameworks/EngineSharded.hpp`:
- `BinanceUserData_Init` + `_Start` after OMS construction (live mode only).
- `BinanceUserData_Shutdown` before adapter shutdown on exit.
- TUI line: WS FILLS status (connected/disconnected), fills received,
  events received.

### phase 06B — error codes + rate limits

`DataStream/BinanceOrderAPI.hpp`:
- `BinanceErrorCode` enum: RATE_LIMIT (-1003), LOT_SIZE (-1013),
  TIMESTAMP (-1021), SIGNATURE (-1022), INSUFFICIENT_BAL (-2010).
- `last_error_code` and `rate_limit_weight` fields on `BinanceOrderAPI`.
- `binance_rest_request` parses `X-MBX-USED-WEIGHT-1m` from response
  headers into `api->rate_limit_weight`.
- `binance_retry_request` stores error code on 4xx, auto-resyncs clock
  on BINANCE_TIMESTAMP (-1021), adds 5s penalty on 418/429 rate limit.

`CoreFrameworks/BinanceAdapter.hpp`:
- worker loop populates `OrderResult.error_code` with actual Binance code
  (was hardcoded -1).

### phase 05 — reconciliation poller

new `CoreFrameworks/ReconciliationLoop.hpp` (~210 LOC):
- `ReconciliationLoopState<F>` with its own `BinanceOrderAPI` instance,
  OMS pointer, `reconcile_queue` SPSC ring, configurable interval (30s)
  and tolerance ($0.01).
- `ReconciliationLoop_Pass`: queries exchange balances via own REST,
  computes expected from `oms->balance`, excludes in-flight orders
  (SUBMITTED/ACKNOWLEDGED buy notional), pushes `CMD_RECONCILE` on drift.
- `ReconciliationLoop_TriggerNow`: external flag for immediate pass
  (called on WS reconnect).
- thread body: interruptible sleep with shutdown + trigger_now checks.

`CoreFrameworks/OrderManager.hpp`:
- `CMD_RECONCILE = 2` added to `CommandType` enum.
- `reconcile_queue` SPSC ring added to `OrderManagerState` (third ring).
- `OrderManager_Tick` drains `reconcile_queue` as third source: sets
  `oms->balance` to exchange-reported value, updates `ks_peak_balance`,
  appends `OEVT_RECONCILED` to event log (mode 1).

`CoreFrameworks/EngineSharded.hpp`:
- `ReconciliationLoop_Init` + `_Start` after user data stream (live mode).
- `ReconciliationLoop_Shutdown` before user data shutdown on exit.
- TUI line: RECONCILE polls, corrections, last drift.

### phase 06C — listen key hardening

`DataStream/BinanceUserData.hpp`:
- `ud_obtain_listen_key`: exponential backoff retry (7 attempts, delays
  0/1/2/4/8/15/30s). shutdown-interruptible waits.
- keepalive thread hardened: retry once after 5s on failure, then signal
  WS reconnect. circuit breaker after 5 consecutive failures across
  reconnects (logs CRITICAL, sets shutdown_requested).
- clock sync: `BinanceOrderAPI_SyncClock` called every keepalive cycle
  (~25 min) on the dedicated REST instance.

## Architecture: Three SPSC Rings

```
  adapter worker ──> result_queue ──┐
  WS user data ───> ws_result_queue ─┼──> OrderManager_Tick (drainer)
  reconciler ─────> reconcile_queue ─┘
```

each ring has exactly one producer and one consumer. no MPSC needed.
drainer drains all three sequentially in Tick.

## Known limitations

- **testnet soak not yet done.** 24-hour live run with fills flowing through
  WS + reconciler. pending testnet credentials.
- **back-to-back REST stress test pending.** 100 sequential orders through
  one BinanceAdapter worker. also pending creds.
- **partial fills deferred to phase 06+.** OMS state machine has ORDER_PARTIAL
  but the code goes straight to FILLED.
- **rejection reset path still TODO.** executor stays in optimistic state
  after a failed order.
- **producer/drainer race on oms->balance** documented but not fixed.
  pre-existing, not OMS-specific.
