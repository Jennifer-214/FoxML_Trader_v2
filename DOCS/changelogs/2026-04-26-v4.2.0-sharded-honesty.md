# v4.2.0 — Sharded honesty pass (2026-04-26)

**Status:** experiment branch only. Under live testing. Not merged to a
release branch, no GitHub release tag, no FoxML_Trader public push.

Six-phase rework closing every place sharded was advertising per-core
semantics it didn't actually deliver. Discovered during a sharded-vs-
legacy parity audit: the per-core engine had per-core *naming* but
single-engine *behavior* in load-bearing places — risk allocation was a
hint not an enforcement, kill switch was account-wide so one bad core
killed three working ones, restarts lost regime hysteresis + ML
confidence + kill-trip state.

## Decisions locked at the start

1. **ANSI TUI** is afterthought; all panel work targets sharded GUI.
2. **Phase 2 model: soft-enforce sizing clamp** (Option B), not hard-
   isolated balance pools (Option A). Single Binance account =
   single balance — Option A would manufacture isolation that doesn't
   exist at the exchange. Soft-enforce mirrors how multi-strategy hedge
   funds run: one fund balance, per-PM risk limits, attributed P&L
   tracking.
3. **Kill reset** lives in a separate Risk panel (read-only Account,
   action-taking Risk).
4. **Persistence: no backward compat with legacy v11.** Refuse those
   files cleanly and start fresh.

## Phase 0 — Legacy live-safety parity

Three live-trading safety features lived in `main.cpp` (legacy path
only) but never made it to `EngineSharded_Run`. Without them, sharded
was unsafe for any actual live use:

- **Orphan BTC recovery on startup**: query exchange balances after
  BinanceAdapter init; if BTC > min_qty, market-sell to recover USDT.
  Use post-recovery USDT as live starting balance (not cfg's value).
- **Force-close on shutdown**: refuse to silently exit with open
  positions. Submits market sells via OrderManager_Submit (same path
  as TP/SL exits), waits up to 30s for the bitmap to clear via
  user-data WS → drainer → OnEvent. Paper mode clears bitmap locally.
- **ReconciliationLoop bug fix**: was pushing CMD_RECONCILE to its
  own `s->reconcile_queue` field, but OMS_Tick reads from
  `oms->reconcile_queue` — drift corrections were silently dropped on
  the floor. One-line redirect to the OMS's queue.

New module: `CoreFrameworks/ShardedLiveSafety.hpp`. Audited against
duplicate code: `BinanceOrderAPI_GetBalances` + `_MarketSell` reused.
The original draft of this work duplicated balance reconciliation —
caught + removed before commit since `ReconciliationLoop_Pass` already
did it (with a more sophisticated inflight-buy adjustment).

## Phase 2.1 — Instrument `core_open_notional`

New per-core counter on `CoreContext`. Sums `(entry_price × qty)`
across currently-open positions. Updated branchlessly in
`EventLoop_OnEvent`:
- Entry: `+= notional`
- Exit: `-= entry_price_snap × qty_snap` — uses the SAME entry-side
  notional we added at entry time, NOT `exit_price × qty`. Asymmetric
  subtraction would leak positive residue per winning trade and
  accumulate unboundedly (after 100 winning trades, budget exhausts
  with zero open positions).

Added 9 assertions including a hammer test (100 round trips with
varied entry/exit prices, mix of winners and losers) that asserts
final notional is exactly zero. The kind of guard that pays for
itself ten times over the next time someone touches that line.

PerCoreSnap exposes `core_open_notional` + `core_budget_used_pct`.
Account panel "Open" column became "Budget" %, color-coded green
<50 / yellow 50-90 / red >90.

Plumbing: hot reload of `risk_pct` / `core_N_risk_pct` now recomputes
`allocated_balance` per core (was set ONCE at startup, silently
stale after any cfg change). Reset Paper zeros all per-core counters.

## Phase 2.2 — Enforce sizing clamp + HALT_CORE_BUDGET

Cross-cutting filter post-process in `EventLoop_RebuildAllParameters`.
Sits on top of every strategy's `_BuildParameters` output (no
strategy code modified). Slow path only.

```
open_notional >= allocated  → trade_size=0, zero-gate w/ HALT_CORE_BUDGET (8)
open_notional <  allocated  → trade_size = min(strategy_qty,
                                (allocated - open_notional) / entry_price)
```

Today (single-position-per-core, sizing = full allocation per trade)
the clamp is mostly defensive — catches a corrupted `intended_qty`,
matters structurally when multi-position-per-core lands.

**Subtle correctness** (caught by tests, fixed pre-commit): `FPN<F>`
is signed. `FPN_SubSat` does NOT clamp at zero on underflow — it
returns a negative. First draft used `FPN_IsZero(FPN_SubSat(...))`
which silently let an over-budget core continue trading with
negative qty. Fix: explicit `FPN_GreaterThanOrEqual(open_n, alloc)` —
honest about sign semantics.

Halt reason 8 added to centralized comment + GUI `halt_names`.

## Phase 3 — Per-core kill switch with MTM

Per-core peak / drawdown tracking on slow path. New CoreContext
fields: `core_peak_balance`, `core_dd_pct`, `core_kill_tripped`,
`core_ks_trips_total`. New cfg: `core_N_max_drawdown_pct` per-core
override, `min_kill_loss` (default $5 floor — prevents tiny-allocation
noise trips), `enable_mtm_kill_switch` (default 1).

Mechanism (slow path, branchless+FPN throughout):

```
current_value = allocated + realized + unrealized
unrealized    = (current_price - entry_price) × qty   [if MTM on + position open]
peak          = FPN_Max(peak, current_value)
dd_pct        = (peak - current_value) / peak
```

Trip fires when BOTH conditions hold:
- `dd_pct > threshold` (per-core override OR global `max_drawdown_pct`)
- `drop > min_kill_loss` (absolute USDT floor)

A kill-tripped core blocks future entries (HALT_CORE_KILL = 9); open
positions ride to TP/SL since SL is the right tool for mid-trade
emergency exit. Aggregate OMS-level breaker stays as backstop.

Manual reset via `TUISharedState::kill_reset_per_core[16]` — engine
slow path consumes the flag, clears trip, refreshes peak to current.

**Why MTM lives on the slow path** (not hot path): kill switch's job
is "stop opening new positions when this core has bled X%." Not
emergency-close — SL handles that on the hot path already. If MTM
ran on hot path, we'd add ~5ns + atomic flag load every tick for a
check whose only output is "should slow path block entries on next
rebuild?" Slow path is the only thing that builds entries — it can
answer that itself.

## Phase 3.5 — Separate Risk panel

New "Risk" panel in DashboardPanels.hpp (sharded only). Per-core
table: Core | Strat | Peak | Curr | DD% | Trips | Status | [Reset].
Reset button writes to `shared->kill_reset_per_core[i]`; greyed out
when armed. Account panel stays read-only / monitoring; risk
controls cluster in one place where you go to take action. Future
home for manual halt, force-close-position, drawdown override slider.

## Phase 4 — Sharded snapshot persistence

Sharded had no persistent state. Every restart lost: per-core regime
hysteresis, pnl_feeder ring buffer, kill switch peak/trips, P&L
counters, position bitmap. After Phase 3 made the kill switch
stateful (peak watermark over core's lifetime), losing it on restart
was a real regression.

New module: `CoreFrameworks/ShardedSnapshotPersist.hpp`. Magic
`0x53484430` ("SHD0") — distinct from `PORTFOLIO_SNAPSHOT_MAGIC` so
legacy v11 files refuse to load cleanly.

**Save model**: atomic rename pattern (write to .tmp, fsync,
rename). Mid-save crash leaves previous good file intact. Final
save on shutdown BEFORE force-close (so persisted state matches
engine intent rather than in-progress liquidation). Periodic save
every 1024 slow-path cycles (~13 min at default cadence).

**Load model**: refuse legacy v11 magic, refuse version mismatch,
refuse core-count mismatch (cfg drift = safer to start fresh than
guess at slot mapping), refuse truncated files (read-into-temp,
commit only on full success). Missing file is not an error.

**Live mode skips load entirely.** Exchange is the truth-of-state
for positions and balance — stale persisted state could disagree
with what's on Binance. Live also has orphan recovery (Phase 0)
and the reconciliation loop. Paper mode is the safe-to-resume case.

## Phase 4.1 — Persist confidence buffers

Pre-4.1, snapshot saved `last_confidence` + prediction snapshots but
NOT the underlying `RollingIC` + `RollingRMSE` ring buffers. After
every restart, `ConfidenceScorer_Compute` returned ~0 conf until
live fills repopulated 64 entries — meaning ML cores stayed
armed-but-inactive post-restart even when paper-trading the same
model that had clearly-visible IC last session.

Bumped `SHARDED_SNAPSHOT_VERSION` 1 → 2. Refuses v1 cleanly. Per-core
block now also writes `ic.predictions[64]`, `ic.actuals[64]`,
`rmse.squared_errors[64]`, plus head/count for each.

`window` field intentionally NOT saved on either struct: it's set
from cfg at `ConfidenceScorer_Init`, so persisting would carry stale
config across restarts if user changed `confidence_window`.

ML cold-start gap closed. After restart, an ML core resumes with the
same confidence the previous session had — paper-soak iteration is
finally additive instead of resetting to zero each time.

## GUI reworks (orthogonal to the safety phases)

Three panels still pretended there was one engine:

- **Market panel**: replaced single-strategy headline with per-core
  breakdown (`MR:1 MOM:1 DIP:2`). Regime relabeled "Core 0 regime"
  since it's per-AUTO-core.
- **Account panel**: added per-core P&L table below the aggregate
  (Core | Strat | Alloc | Realized | Fees | W/L | Budget). Aggregate
  stays as the OMS-wide summary.
- **Settings panel**: per-core stuff was split — hot-swap dropdown
  in standalone "Per-Core Strategy" panel, but `core_N_risk_pct` /
  `core_N_model_path` in Settings → Per-Core tabs. Folded everything
  into one "Core Configuration" section per tab. Standalone
  Per-Core Strategy panel removed.

## Things deliberately deferred

- **Partial exits in sharded**: edge-amplification, not edge-finding.
  Without a confirmed signal, partial exits is theoretical
  optimization. The plan stays in `plans/post-v4.0-followups.md` for
  when there's a model with edge to optimize.
- **ANSI TUI display reworks**: GUI is the only product Jenn uses;
  ANSI build target stays compiling but skips display reworks.
- **Per-core data streams + per-core charts**: deferred until the
  single-feed/single-chart actually feels limiting in real use.

## Hot path verification

Walked every phase against the branchless-FPN doctrine. **Hot path
untouched.** All new state lives on `CoreContext` (slow-path data
structures); all new checks happen in `EventLoop_RebuildAllParameters`
(slow path) or `EventLoop_OnEvent` (slow path). 40-400ns p99 hot
path target preserved — `ExecutionCore_Tick` / `BG_Evaluate` /
`SG_Evaluate` are not modified.
