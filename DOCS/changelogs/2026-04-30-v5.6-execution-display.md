**Date:** 2026-04-30
**Branch:** `feat/v5.6-display-visibility` (forked from
`experiment/per-core-sharding`)

**Hot path:** untouched in all six ships

## Trigger

Live paper run on 2026-04-30 showed DIP core continuously in "READY"
status while making zero trades, including missing a clearly profitable
dip-and-recover sequence. Investigation traced the silent-block to a
fee-floor `GATE_FLAG_BUY_BLOCKED` set by
`StrategyParameters.hpp:884` — the strategy was correctly refusing
fee-eating trades, but the GUI's "READY" predicate ignored the flag
entirely. Operator was looking at one truth model, hot path at another.

## Root cause class

Recurring bug pattern Class 2c (sub-pattern of "display ↔ execution
divergence"): **the display predicate is a strict subset of the
hot-path predicate.** Hot path enforces:

```
bg_fires  = price_ok & volume_check & ~blocked_mask
can_enter = ~any_active & permission & bg_fires
```

The pre-v5.6 GUI Status column checked `price_ok` only — 1 of 5 terms.
Any term checked by the hot path but NOT the GUI produces "looks
ready, isn't ready" misleading state.

Three independent BUY_BLOCKED paths were silently active in production:
fee-floor (StrategyParameters.hpp:884), cost-gate (:919), book-imbalance
(ControllerEventLoop.hpp:1846). All three caused entries to be refused
with no GUI explanation. Plus halt_reason=10 (book-imbalance) was set
in code but invisible — `halt_names[]` had only indices 0-9 with bound
`< 10`.

## Outcome

The 2026-04-30 missed-trade screenshot is now interpretable. With
v5.6 active a DIP core in the same scenario shows:

```
Core 3  DIP   $76591.02  +0.141%  BLOCKED: fee-floor
```

…instead of "wait" / "off". And in collapsing detail:

```
  tp_pct: 0.130% / floor 0.150%
```

…explaining the *why*. The same information lands in `health.jsonl`
on every transition, so post-hoc forensics is `jq`-tractable.

## Recurring-bug map update

Class 2c (display predicate strict subset) added to
`DOCS/RECURRING_BUG_PATTERNS.md`. Future PRs adding new hot-path
predicate terms must add a corresponding GUI surface in the same PR
or fail readiness check 12 (display↔execution invariant).

- **Per-strategy SHALT codes** (`SHALT_NO_UPTREND`, `SHALT_NO_MEAN_REV`,

  the prerequisite (without diagnostic readout you can't tell
  wrong-signal from right-signal-bad-luck).

## Lessons / process notes

- The audit-first split on Phase 5 paid off: ~5h saved by verifying
  before fixing. Codifying "Phase Na audit / Nb fix" as a pattern in
  the readiness skill seems like a good idea.
- Single-source rule was load-bearing for Phase 4 — refactoring the
  controller's gate checks to expose comparands inline (rather than
  exposing them via separate Gate_*Diagnostic helpers as originally
  proposed) kept the change small and didn't churn the call sites.
- Hot path stayed clean across all six ships. The display layer
  carries 100% of the v5.6 changes; the hot path predicate is exactly
  where it was at v5.5.6.
