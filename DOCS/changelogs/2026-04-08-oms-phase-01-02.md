# 2026-04-08 — v3.9.0-experiment: OMS Phase 01 + 02 (Order Struct + Async Submission)

scope: experimental branch `experiment/per-core-sharding`. follow-on to the
sharded live trading wiring at `pre-oms` tag. lifts orders to first-class
status with a real state machine, then makes submission async via an
exchange adapter so the drainer never blocks on REST. paper mode is
unchanged; per-core latency stays at the 57 ns floor. live mode is
structurally identical for the user but the order flow now goes through
a per-thread worker pool with proper lifecycle tracking.

planning: see `plans/oms/master.md` and `plans/oms/01_*/plan.md` +
`plans/oms/02_*/plan.md`. the survey that drove this work is in the
session log; key findings (BinanceOrderAPI is not thread-safe, the
"persistent connections" claim in master.md was wrong) are baked into
the corrections in those plan files.

## Shared

- new constants in `Limits.hpp`:
  - `MAX_INFLIGHT_ORDERS = 16` — caps the OrderManager order table.
    pinned at 16 so the slot bitmap stays uint16_t. easy to widen.
  - `MAX_BINANCE_WORKERS = 4` — caps the BinanceAdapter worker thread
    pool. each worker owns one BinanceOrderAPI instance because the
    underlying client is not thread-safe.
- `plans/oms/master.md` corrected: the "BinanceOrderAPI uses persistent
  connections" claim was false. the code at
  `DataStream/BinanceOrderAPI.hpp:341-345` explicitly closes the socket
  and destroys the SSL session after every request. TLS handshake is
  paid per request, not amortized. the OMS plan still wins because the
  headline improvement is async drainer (drainer cycle drops from 800 ms
  worst case to sub-µs), not connection reuse. master.md now says so
  explicitly. also added a thread-safety warning so future-readers don't
  accidentally use a single shared BinanceOrderAPI.

## Execution Engine

### phase 01 — order struct + synchronous OMS skeleton

5 new headers in `CoreFrameworks/`:

- `Order.hpp` — first-class order entity with full lifecycle state
  machine (PENDING / SUBMITTED / ACKNOWLEDGED / PARTIAL / FILLED /
  REJECTED / CANCELED / TIMEOUT / UNKNOWN). carries id, client_id,
  exchange_id, core_id, type, requested_qty, filled_qty,
  avg_fill_price, retry_count, timestamps. `Order_Init` zero-fills and
  sets state = PENDING. `Order_IsTerminal` predicate for the OMS to
  decide when to free a slot. naming clarifier in the file header so
  future-readers don't conflate this with `MemHeaders/PoolAllocator.hpp::OrderPool`
  which is the buy gate's intent pool, totally unrelated.
- `OrderManager.hpp` — single-owner OMS that lives on the drainer
  thread. owns the in-flight order table (bitmap-allocated like the
  rest of the codebase). phase 01 version: `OrderManager_Submit`
  allocates a slot and sets state PENDING; `OrderManager_Tick` walks
  the bitmap and synchronously calls `BinanceOrderAPI_MarketBuy/Sell`
  for each PENDING order, marks FILLED or REJECTED. blocks the
  drainer for the full REST round trip (~50-200 ms per order on
  testnet). the structural win is that orders are now first-class
  entities; the perf win waits for phase 02. (later overwritten by
  the phase 02 async version in this same commit — the file you read
  at HEAD is the phase 02 version.)
- `ShardedOrderLatency.hpp` — extracted from `EngineSharded.hpp` so
  `OrderManager.hpp` could call `Sample` without forming a circular
  include. the file-static instance still lives in `EngineSharded.hpp`
  so the existing TUI render loop reads the same numbers; the
  type and helpers moved to the new header. comment block preserves
  jennifer's original phrasing.

modifications to `EngineSharded.hpp`:
- new `OrderManagerState<F> oms` declared after `EventLoopState_Init`
- `OrderManager_Init` called with the live_trading flag
- drainer lambda capture list gains `&oms`
- the inline LIVE ORDER SUBMISSION block (~25 lines of
  `BinanceOrderAPI_MarketBuy/Sell` + steady_clock + sample + log)
  replaced with a single `OrderManager_Submit` call
- `OrderManager_Tick` called after each per-core drain pass and after
  each post-producer drain pass
- `OrderManager_Shutdown` called after all threads join
- inline `ShardedOrderLatency` definition removed (now lives in its
  own header). the file-static instance and the existing
  `ShardedOrderLatency_Reset` call site stayed.

### phase 02 — async submission via exchange adapter

2 more new headers:

- `ExchangeAdapter.hpp` — generic exchange interface as a
  function-pointer-in-struct (matches the project's "C-style with
  templates, no classes" convention from CLAUDE.md). carries
  `submit_market_buy` / `submit_market_sell` (async, return
  immediately, callback fires later), `get_balances` /
  `query_order` (synchronous slow-path queries), and `shutdown`.
  `OrderResult` is non-templated POD so it flows through SPSCRing
  slots without depending on the FPN<F> width. `OrderCallback`
  typedef is the contract the adapter calls back through.
- `BinanceAdapter.hpp` — concrete adapter wrapping
  `DataStream/BinanceOrderAPI.hpp`. **uses per-thread BinanceOrderAPI
  instances**, NOT a single shared instance with a mutex. the file
  header has a long comment block explaining why: the underlying
  client mutates `sockfd`, `ssl`, and `connected` on every request
  (`BinanceOrderAPI.hpp:67-80`) and concurrent calls would corrupt
  state. one `BinanceOrderAPI` per worker, owned exclusively by one
  thread for its entire lifetime. memory cost is trivial (~few KB
  per worker including the SSL_CTX). the comment block also says
  "NEVER refactor this to a shared instance with a mutex" because
  that would add contention without solving the back-to-back heap
  corruption history (`CHANGELOG.md` 3.0.19, 2026-03-24).

  the worker thread loop pops `PendingSubmission` from the SPSC
  submission queue, calls `BinanceOrderAPI_MarketBuy/Sell` on its
  own per-thread instance, brackets the call with `steady_clock`
  and samples into `ShardedOrderLatency` (so the TUI keeps reading
  the same instance), builds an `OrderResult`, and invokes the
  callback. the callback (`OrderManager_FillResultCallback<F>` from
  `OrderManager.hpp`) pushes a `CMD_FILL_RESULT` into the OMS
  result queue and returns. drainer thread drains the result queue
  on its next `OrderManager_Tick` pass.

  **worker_count = 1 for this commit**. the 2026-04-08 survey
  recommended starting at 1 to validate the async pipeline without
  exposing the back-to-back heap corruption class. once a 24-hour
  testnet soak is clean, scale to 2-4 in a follow-on commit. the
  trade-off when scaling: 1 worker serializes orders (~50-200 ms
  each on testnet) but maintains arrival order. N workers complete
  in parallel but lose arrival order. for single-asset trading the
  ordering loss is mostly cosmetic.

`OrderManager.hpp` rewritten for phase 02:
- holds an `ExchangeAdapter<F>` by value (zero-initialized in paper
  mode = all function pointers null = the OMS short-circuits before
  touching them)
- new SPSC `result_queue` of `Command` records. adapter worker is
  the sole producer (with worker_count==1), drainer's
  `OrderManager_Tick` is the sole consumer
- `OrderManager_Submit` paper mode: bumps total_submitted /
  total_filled, returns next id. zero adapter cost in paper mode.
- `OrderManager_Submit` live mode: allocates slot, calls
  `adapter.submit_market_buy/sell` with the OMS as user_ctx and
  the `OrderManager_FillResultCallback<F>` as the callback. async
  — never blocks on the network.
- `OrderManager_Tick` drains the result queue, looks up each
  matching order by id, marks FILLED or REJECTED, frees the slot.
  linear search across 16 slots is trivial.
- callback `OrderManager_FillResultCallback<F>` is the only path
  by which the worker thread mutates OMS state. it pushes one
  Command and returns. all real state mutation happens on the
  drainer thread inside Tick.

`EngineSharded.hpp` updated to use the adapter:
- `static BinanceOrderAPI g_sharded_order_api` → `static BinanceAdapterState g_sharded_binance_adapter`
- `BinanceOrderAPI_Init` call → `BinanceAdapter_Init` (passes
  worker_count = 1 with an inline comment pointing at the
  scaling decision)
- abort path's `BinanceOrderAPI_Cleanup` → `BinanceAdapter_ShutdownState`
- OMS init now constructs `ExchangeAdapter<F> exchange_adapter{}`
  (value-initialized = paper mode default, all pointers null)
  and overwrites it with `BinanceAdapter_Get<F>(&g_sharded_binance_adapter)`
  if `live_trading` is set
- final cleanup at end of `EngineSharded_Run` calls
  `BinanceAdapter_ShutdownState` only if live_trading was set

### why this changes the drainer cycle from 800 ms to sub-µs

before phase 02: drainer thread inside `EngineSharded_Run` called
`BinanceOrderAPI_MarketBuy/Sell` directly inline. with 4 cores firing
events simultaneously, worst case was 4 × 200 ms = 800 ms drainer
cycle. all 4 per-core SPSC event rings could back up while the drainer
was blocked on a single REST call. this is the actual
"executor-can't-re-enter-because-drainer-is-blocked" pathology the OMS
exists to fix.

after phase 02: drainer just calls `OrderManager_Submit` which
enqueues to the adapter's worker thread and returns. the worker
thread does the REST call on its own pinned thread, on its own
BinanceOrderAPI instance. drainer cycle is back to sub-µs.

per-core hot path is **completely untouched** by either phase. the
57 ns / 61 ns / 89 ns floor stays exactly as it was — no changes to
`ExecutionCore.hpp`, no changes to the gate evaluators, no atomics
added. the cache opt commit's measurements still hold.

## Known limitations (carry-over to phase 03+)

- **rejection reset path is still a TODO.** when an order fails, the
  OMS marks it REJECTED and frees the slot, but the executor on the
  per-core hot path is still in its optimistic state (active=1 after
  a failed entry, active=0 after a failed exit). matches the legacy
  fire-and-forget pattern. the comment at the OMS_Tick failure
  branch explicitly says "TODO reset path" — the proper fix lands
  in phase 03 (event log) when events stop optimistically updating
  the portfolio in `OnEvent` and instead get folded from the OMS
  result stream.
- **fill price reconciliation is missing.** `EventLoop_OnEvent` still
  uses the executor's detected price, not the actual fill price the
  worker reported. on a fast moving market the gap is a few basis
  points. same fix as above — phase 03.
- **partial fills not handled.** the OMS state machine has the
  ORDER_PARTIAL state but phase 02 only ever transitions to FILLED
  or REJECTED. binance returns total executedQty so this works for
  market orders that fully fill (the common case). limit orders
  and partial fills wait for phase 06.
- **back-to-back stress test not yet executed.** phase 02 acceptance
  criterion #7 requires 100 sequential orders through one
  BinanceAdapter worker on testnet to verify no crash from the
  back-to-back heap corruption class. needs testnet credentials and
  a real REST endpoint. block phase 02 ship on this before going
  live.
- **worker pool stays at 1.** scaling to 2-4 is a follow-on commit
  after the soak test passes.
- **no new TUI display for OMS counters.** `OrderManager_TotalSubmitted`,
  `_TotalFilled`, `_TotalRejected` are exposed via helpers but the
  existing `EngineSharded.hpp` TUI render loop still shows the
  per-core latency table and the order latency line, not the OMS
  counters. easy follow-up — one new line in the render loop.
- **no new unit tests for the OMS state machine.** phase 01 plan
  estimated ~150 LOC for OMS unit tests, phase 02 plan estimated
  ~250 LOC. both deferred to a follow-up commit. existing
  `controller_test` (279 assertions) still passes — the OMS work
  doesn't affect the legacy single-core path.
