**Date:** 2026-04-27
**Branch:** `experiment/per-core-sharding`
**Status:** experiment branch — under testing, not released

## Summary

First post-Track-E feature batch. Three new state structs feed seven
new `FEAT_*` constants for the v4.5 feature pack:

- **D.1 — book imbalance over time** (3 features): a ring buffer
  of recent `book_imbalance` samples (1024-sample window). Emits
  `book_imb_mean_short` (mean of last 64 samples), `book_imb_mean_long`
  (mean over full window), and `book_imb_drift` (current minus
  mean_long). Catches "imbalance has been one-sided for the last 30s"
  signals that the current-tick book_imbalance feature can't capture.
  Unblocked by Track E.3 (depth replay): backtest now sees the same
  imbalance time series live does.

- **D.2 — signed-volume EWMAs** (3 features): three exponentially-
  decaying weighted moving averages of signed trade volume at
  half-lives 10s / 1m / 5m. Sign convention: taker buy = positive,
  taker sell = negative (mirrors `CumDelta_Push`). Decay uses
  `exp(-dt/halflife)` with dt computed from tick timestamps —
  cadence-independent and works in both backtest (CSV-stored
  timestamps) and live (real wallclock). Emits `flow_10s`,
  `flow_1m`, `flow_5m`.

- **D.4 — large-trade z-score** (1 feature): rolling window of
  recent trade sizes (1024 samples). Emits `large_trade_z` =
  (current_size - window_mean) / window_stddev. Captures whale
  events as a normalized signal regardless of typical trade size
  per asset.

## Files added

- `ML_Headers/FlowFeatures.hpp` — new header defining
  `BookImbalanceHistory<F, W>`, `FlowState`, `LargeTradeState<F, W>`
  + their Init/Push/accessor functions. `BookImbHistory_Push`
  maintains a running sum for O(1) MeanLong; `MeanShort(k)` walks
  the last k samples, O(k). `FlowState` stores three doubles +
  last timestamp; first push seeds without decay, subsequent
  pushes decay then add. `LargeTradeState` keeps running
  `sum + sum_sq` for O(1) mean+variance; z-score is
  `(current - mean) / sqrt(var)`. All three follow the four-site
  rule (Init zeros, Push grows, ring eviction subtracts the
  evicted contribution from the running sums).

## Cadence — train-serve parity check

All three new states push at slow-path cadence (every
`cfg.poll_interval` ticks ≈ 100 ticks default, ~1-2s in busy
markets). Both sharded paths push with the same inputs:

- BookImbalanceHistory: pushes `book_imbalance` from depth state
  (live: `DepthSharedState::snapshots[active]`; backtest:
  `DepthReplayState::current`). Symmetric.
- FlowState: pushes `(timestamp, signed_volume)`. Live timestamp
  is `ts_us` (BinanceStream wallclock); backtest is
  `tick.timestamp` (CSV-stored historical). Decay computes
  `dt = current_ts - last_ts` in microseconds → seconds, so the
  EWMA approximates the same continuous-time decay regardless of
  cadence. Train-serve parity holds.
- LargeTradeState: pushes `tick.volume`. Identical inputs both
  paths.

Both paths use the same `Regime_ComputeSignals` call (Track E
single-source-of-truth), so the produced features are byte-
identical given the same input stream — modulo the documented
timestamp-precision differences from Track E.

## What changes for users

- **Old models fail load.** `MODEL_FORMAT_VERSION` v2 → v3.
  The `Model_Load` version check refuses pre-v4.5 models (v2)
  loudly instead of silently producing garbage features. Users
  must retrain at v4.5 to use D.1/D.2/D.4 features. The Past
  Runs viewer's pre-v4.5 entries remain readable; they just
  reference models that won't reload.
- **`models/` directory contents become stale.** Any v3.x or
  v4.0-v4.4 model file in `models/` will fail load with
  "MODEL_FORMAT_VERSION mismatch (got 2, want 3)". Move them
  aside or retrain.
- **`MODEL_MAX_FEATURES` 32 → 64.** Any fixed-size buffer in
  user code or scripts that hardcoded 32 needs to grow. Internal
  buffers updated automatically.
- **No cfg field changes** — Wave 1 doesn't introduce new cfg
  fields. The new states use compile-time fixed window sizes
  (1024 samples). Tuning would require editing `FlowFeatures.hpp`
  template defaults; deferred to "see if it matters first."

## Master roadmap status

After Wave 1 (this release), the sequence continues with:

- **Wave 1 retrain decision point**: train + walk-forward at
  v4.5 features. If val accuracy clears majority baseline by
  >5% → continue to D.3. If not → skip to C.3 (maker-only
  execution).
- **Wave 2 (~1 week)**: D.3 (spread dynamics — `spread_bps`,
  `spread_zscore`). Reads from `BookSnapshot::spread`. Bumps
  `MODEL_FORMAT_VERSION` v3 → v4.
- **Wave 3 (~1-2 weeks)**: C.3 (maker-only execution).
  Independent of feature work; can be sequenced before or after
  Wave 2 depending on how fast the model retraining tells us
  which features matter.
