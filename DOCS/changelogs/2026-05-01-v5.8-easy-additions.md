# v5.8 — Easy Additions: X-macro registries everywhere

**Date:** 2026-05-01
**Branch:** `feat/v5.8-easy-additions`
**Tags:** `v5.8.0` → `v5.8.4c` (8 ships across 6 phases; 0+1+2a+2b+3+4+5+5b+5c, plus this final 5)
**Tests:** 938 → 1030 (+92 across 5 EXTENSIBILITY blocks)
**Hot path:** untouched in every v5.8 ship — every change is slow-path
or display-time

## Trigger

Two forcing functions converged in late April 2026:

1. **Strategy plug-and-play idea was parked** in
   `DOCS/STRATEGY_REFACTOR_IDEAS.md` waiting for "next strategy add"
   trigger. The original 5-strategy codebase was manageable; adding a
   6th would have required touching 8 sites, and the cost of
   forgetting one of those sites had been demonstrated multiple
   times (orphaned `_Init`, missing GUI dispatch, halt-name mirror
   drift in v5.6.0).

2. **Feature registry needed for v5.9 ML hardening.** Standardization
   (persisted train-time mean/std), leakage sentinels, and walk-
   forward stability all want to index by stable `FeatureId`. Without
   the registry, v5.9 would have to build its own parallel naming
   system.

Doing both together = one refactor sprint, two registries with the
same shape, codebase gets a consistent extensibility pattern.

This is a **pure refactor sprint, not a feature sprint.** No new
operator-visible behavior. Every change is "the same thing, with
fewer places to forget to update."

## Phase 5b — Stateful GUI panel registry (`v5.8.4b`, `5f78688`)

Added `FOREACH_PANEL(X)` to `GUI/GuiThread.hpp` covering the 4
stateful panels (TradeHistory, LogViewer, Settings, StrategyQuality).
Stateless panels (BuyGate, Market, Account, Positions, Risk, Stats —
the 10 panels that take only `snap`) NOT in the registry — they take
no state, so a registry would add no value.

Decision (user-approved): stub `_Init` for every panel rather than
NULL-allowed dispatch. Diverges from v5.8.0's SimpleDip NULL-Adapt
precedent because `_Init` is the universal entry point whereas
Adapt is per-strategy optional.
- `Settings_Init` wraps existing `Settings_Load` semantics
- `tt::StrategyQuality_Init` is a no-op zero-ensure stub (state has
  default member initializers; loads on Refresh button)

Render dispatch left hand-coded — the 4 render fns have non-uniform
signatures (TradeHistory takes `(state*, int)`, Settings takes 5
args). Uniformizing renders is a separate ship that subsumes the
deferred render-thread I/O cleanup (`LogViewer_Refresh` +
`TradeHistory_Refresh` perform synchronous `stat()`/`fopen()`/`fread()`
on the render thread — known maintenance debt, filed for v5.8.x).

## Phase 5c — Backtest metric helpers + drift fix (`v5.8.4c`, `408664b`)

The heaviest phase in this sprint. Deep readiness audit caught **3
cross-site formula drifts** that would have silently corrupted
optimizer rankings. Each got reconciled to a single canonical helper.

New file: `CoreFrameworks/MetricCompute.hpp` — neutral location so
both runtime (`EngineTUI`, `ShardedSnapshot`) and backtest
(`BacktestEngine`, `BacktestSharded`) can include without crossing
the runtime → backtest-suite layering boundary. Earlier draft
accidentally placed helpers in `BacktestEngine.hpp`; moved before
commit.

### Drift #1: profit_factor — 4 sites, 4 different formulas

Pre-v5.8.4c:
- `BacktestEngine.hpp:378` → `(gl > 0.0001) ? gw/gl : 0.0`
- `BacktestSharded.hpp:703` → `cumulative_wins / cumulative_losses`
  (no guard — divides by zero if losses=0)
- `EngineTUI.hpp:461` → `(g_losses > 0.001) ? g_wins/g_losses : 0.0`
  (different epsilon: 0.001 vs 0.0001)
- `ShardedSnapshot.hpp:335` → `g_wins_d / g_losses_d`, returns
  `-1.0` sentinel for "all wins, no losses" case

**Latent accounting bug:** the `-1.0` sentinel was consumed by the
optimizer at `BacktestEngine.hpp:1566` (`OPT_METRIC_PF`). When the
walk-forward optimizer maximized `profit_factor`, a sharded run with
all wins (sentinel = -1.0) got ranked LOWER than a mediocre run
(`profit_factor = 1.5`). Perfect-wins config silently lost to mediocre.

**Fix:** canonical `Compute_ProfitFactor(gw, gl) = (gl > 0.0001) ? gw/gl : 0.0`.
Dropped the `-1.0` sentinel entirely. Added `int all_wins_run` field
to `BacktestStats` + `TUISnapshot` for distinct GUI/TUI rendering
("∞" / "—"). Math + display cleanly separated.

### Drift #2: expectancy — 3 sites, fabs() inconsistency

Pre-v5.8.4c:
- `BacktestEngine.hpp:383` → uses `fabs(avg_loss)`
- `EngineTUI.hpp:1356` → no fabs
- `ShardedSnapshot.hpp:345` → no fabs

Harmless when `avg_loss` invariant-negative; defensive against future
sign-flip bugs.

**Fix:** canonical `Compute_Expectancy` keeps `fabs(avg_loss)`. Added
comment explaining the invariant + why fabs is defensive-redundant.

### Drift #3: max_drawdown — two independent implementations

Pre-v5.8.4c:
- `BacktestEngine.hpp:405-416` (post-hoc walk over equity curve)
- `BacktestSharded.hpp:508-660` (incremental tracker, per-tick)

Formally equivalent but **formal equivalence ≠ bytewise FP equivalence**
— different summation orders can yield 1-ULP drift. If the optimizer
or WF gap detector ever compared sharded vs backtest stats on the
same run, drift could fire false signals.

**Fix:** extracted shared `MaxDrawdown_UpdateIncremental` helper.
`BacktestStats_ComputeFromEquity` calls it once per equity sample
in its post-hoc loop; `BacktestSharded` calls it per-tick. Same code
path, same FP ops, same rounding → **bytewise identical by
construction**, no regression test required. Eliminates an entire
drift class structurally rather than catching it via tests.

### Metric registry

`FOREACH_BACKTEST_METRIC(X)` is metadata-only (name + printf format),
not dispatch. The `Compute_*` helpers take varying input shapes
(equity arrays vs scalar inputs) and aren't function-pointer
dispatchable. The registry powers display-side loops (e.g. metric
panels that iterate names + formats).

## Cross-cutting invariants enforced

1. **Hot path UNTOUCHED across every ship.** All registries are
   slow-path / display-time. Live `ExecutionCore_Tick` /
   `BG_Evaluate` / `SG_Evaluate` paths reference none of the
   registry mechanisms — only the values they generate at slow-path
   build time.
2. **Existing trained models continue to load** OR force-invalidate
   via `MODEL_FORMAT_VERSION` rejection. `FEATURE_REGISTRY_HASH`
   change means a deliberate retrain decision.
3. **Public/private split preserved.** `__has_include` guards on
   `private/EmaCross.hpp` work in both Strategy registry (Phase 1)
   and Regime registry (Phase 5).
4. **No silent orphans.** `tools/calls_graph_diff.sh` ran clean
   before and after every phase. The X-macro discipline + the loop
   tests in `// === EXTENSIBILITY ===` sections enforce
   "every X-macro entry has a real implementation."
5. **Per-phase tag + push immediately.** Filesystem-crash incident
   discipline (2026-04-30) — every phase committed + tagged + pushed
   to `origin` before next phase started.
