**Date:** 2026-04-27

**Prerequisite:** v4.6 (Wave 2 features)

## Summary

Two-position-per-core partial exits land in sharded. When
`cfg.partial_exit_enabled=1`, each entry signal opens BOTH leg A
(at TP1) and leg B (at TP2 = TP1 × tp2_mult), sharing SL. Either or
both can exit independently; shared SL closes both on the same
tick. The hot path's branchless dual-leg SG_Evaluate adds ~1-2ns
per tick, well within the 500ns p99 budget.

Two bug fixes ship alongside, both surfaced by live engine_gui
testing during this session: time-exit underflow on stale snapshot
`last_entry_tick`, and snapshot loader missing the `ExecutionCore`
hot-path re-activation. Both manifested as "positions don't clear
after SL/TP fires" — they were independent bugs with the same
visible symptom.

- Wired into both `EngineSharded_Run` (live) and
  `BacktestSharded_Run` (backtest) startup paths.
- 18 controller_test assertions.

### P.2 — Hot-path dual-leg SG (commit `b99fb48`)
- `TradeEvent.leg` field (uint8_t, stolen from existing pad).
  `PARTIAL_LEG_A` / `PARTIAL_LEG_B` constants in `TradeEvent.hpp`.
- `GateParameters` gains `tp_pct_b` (FPN<F>) +
  `GATE_FLAG_PAIR_ACTIVE = 0x40`.
- `ExecutionCore<F>` gains `active_b`, `entry_price_b`,
  `live_tp_b`, `live_sl_b`. `Init` zeroes them.
- `ExecutionCore_Tick` rewritten with dual-leg branchless SG:
  - Both legs' TP/SL comparisons run unconditionally
  - `active_a` / `active_b` masks gate which fires
  - `can_enter` requires `~(active_a | active_b)` — prevents leg A
    re-opening solo while leg B still runs
  - Up to 2 events per tick (shared SL hits both legs)
  - Entry path activates leg B from `tp_pct_b` when
    `GATE_FLAG_PAIR_ACTIVE` is set; leg B's SL is shared with A
- 22 controller_test assertions covering all leg-firing patterns
  (pair off, pair on entry, leg A solo TP, shared SL).

### P.3 — OMS leg-aware drainer (commit `f1a18e7`)
- `Order.leg` field. `Order_Init` defaults to 0.
  `OrderManager_Submit` takes optional `leg` parameter.
- `EngineSharded` drainer maps `(event.core_id, event.leg)` →
  portfolio slot via `Sharded_LegSlot`. Defensive log + skip on
  malformed combos.
- Entry qty splits by `cfg.partial_exit_pct`: leg A gets
  `partial_pct`, leg B gets `1 - partial_pct`. Disabled mode: full
  qty to leg A, no split.
- Exit qty reads from `portfolio.positions[portfolio_slot]`.
- `last_entry_tick` / `last_entry_price` / `active_prediction`
  stamped only on **leg A** entry (one trade = one stamp).

### P.4 — Strategy dispatcher cap (this commit)
- `Strategy_BuildParameters` post-dispatch uniform cap. After the
  per-strategy `_BuildParameters` returns, the dispatcher applies:
    - When `cfg.partial_exit_enabled=1`:
      `out->flags |= GATE_FLAG_PAIR_ACTIVE`,
      `out->tp_pct_b = out->tp_pct * cfg.tp2_mult` (fallback to
      `tp_pct` if `tp2_mult=0`).
    - When disabled: explicit clear of both fields (safe re-use of
      `GateParameters` instances).
- All five strategies (SimpleDip, MeanReversion, Momentum, EmaCross,
  ML) inherit partials support uniformly — adding a new strategy
  doesn't need partial-exit awareness in its `_BuildParameters`.
- 5 controller_test assertions covering enabled/disabled/defensive
  paths.

## Bug fixes shipped alongside

### `last_entry_tick` snapshot drift (commit `b86b17f`)
**Symptom:** engine.log spammed with
`time-exit (held 18446744073709536760 ticks, gain -X.X%)` after
restart with active snapshot positions. Time-exit submitted
spurious SELL orders that piled up against the genuine SL exit,
preventing slots from clearing in the GUI Positions panel.

**Root cause:** `ticks_produced` resets to 0 each engine session,
but `last_entry_tick` persists in `ShardedSnapshotPersist.hpp`.
After restart, `entry_t > now_tick` → uint64 subtraction
underflows to ~2^64 → time-exit `elapsed >= max_hold_ticks`
trivially passes.

**Fix:** defensive guard in `EngineSharded.hpp` time-exit block.
When `entry_t > now_tick`, log the drift, reset `entry_tick =
now_tick`, skip this cycle. CLAUDE.md "Snapshot Tick-Counter
Drift" section documents the pattern for future code.

### Snapshot ExecutionCore re-activation (commit `777f843`)
**Symptom:** position visible in GUI Positions panel, price below
the position's stop-loss, but position never closes. SL markers
visible on chart but no actual exit fires.

**Root cause:** snapshot persists `Position` fields (entry_price,
take_profit_price, stop_loss_price, quantity) but NOT the
`ExecutionCore` hot-path mirrors (`active`, `live_tp`, `live_sl`,
`entry_price`). After load: `portfolio.active_bitmap` has bits
set, `portfolio.positions[slot]` is restored, but
`ExecutionCore.active = 0` (init default). Hot path's
`can_exit = active & sg_fires` is always 0 → SG never fires →
zombie position.

**Fix:** in `ShardedSnapshot_Load` after the existing portfolio +
core-context restoration, walk the active_bitmap and copy each
restored Position's fields into the matching ExecutionCore's
hot-path mirrors (set active=1). Boot order ensures this runs
before per-core threads start, so non-atomic writes are safe.
9 controller_test assertions verifying the re-activation
behavior.

## Cfg fields (all already existed pre-Wave-1)

```
partial_exit_enabled = 0    # 0 (default, pre-P.1 behavior) | 1
partial_exit_pct     = 0.5  # fraction at TP1; remainder rides TP2
tp2_mult             = 2.0  # TP2 distance = tp_pct × this
breakeven_on_partial = 1    # P.4 doesn't wire this; deferred
```

To enable: set `partial_exit_enabled=1` in `engine.cfg` (live) or
`backtest.cfg` (backtest). Validation will refuse if more than 8
cores configured. Default cfg (= disabled) preserves all
pre-partial-exit behavior bit-for-bit.

## Deferred to follow-ups

- `breakeven_on_partial` semantics — slow path should ratchet leg
  B's SL to entry_price after leg A's TP1 fires. Currently leg B's
  SL stays at the original shared SL.
- Snapshot persistence of `live_tp_b` / `active_b` /
  `entry_price_b` — current snapshot v8 doesn't include these. A
  snapshot taken with both legs active won't restore leg B
  correctly. Acceptable today: snapshot save runs periodically;
  failure mode is "leg B closes at next tick that hits its TP/SL"
  which matches single-leg semantics.
- Hot-path latency measurement run with `LATENCY_PROFILING=ON` to
  formally verify the +1-2ns estimate. Existing per-core panel
  shows the live measurement; explicit histogram dump is the gate
  if needed.
