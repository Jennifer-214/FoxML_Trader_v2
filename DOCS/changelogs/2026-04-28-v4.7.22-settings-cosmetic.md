# v4.7.22 — Settings panel cosmetic cleanup

**Date:** 2026-04-28
**Branch:** experiment/per-core-sharding

P1 of the settings audit (`plans/2026-04-28-settings-audit.md`). Cosmetic cleanup pass — no semantic cfg changes, no wire-up changes. Just makes the panel honest about the engine's actual state.

## What landed

### 1. Killed duplicate field renders

`momentum_tp_mult`, `momentum_sl_mult`, `momentum_breakout_mult`, `emacross_dip_mult`, `emacross_crossover_min` each appeared in TWO sections of `field_defs[]` — once under their own legacy section ("Momentum" / "EMA Cross") and again under their `*Tuning` section. Both rendered. Editing one didn't update the other immediately. Confusing.

Dropped the legacy "Momentum" and "EMA Cross" sections from `field_defs[]`. Moved `momentum_r2_min` and `emacross_trail_mult` into "Momentum Tuning" / "EMA Cross Tuning" so no fields disappear from the GUI. Each field now renders exactly once.

### 2. "Per-Core (Experimental)" → "Per-Core"

Sharded execution has been canonical for many versions; CLAUDE.md states "Sharded is production. Legacy single_core LIVE is deprecated (warned at boot)." The "Experimental" suffix on the section was misleading.

Tooltip on `engine_mode` updated:
- Before: "Per-core risk-sharded execution (experimental). OFF (default): legacy single-threaded engine. ... Uses synthetic ticks until Binance feed wiring lands."
- After: "Per-core risk-sharded execution (production default). ON (default): per-core architecture, controller owns the portfolio, each execution core runs one position at a time on its own thread. OFF: legacy single-threaded engine — DEPRECATED, warns at boot."

(Synthetic ticks claim was outdated — Binance feed has been wired since v3.x.)

### 3. "0 Cores" widget display fix

`num_execution_cores` widget showed 0 when the cfg file didn't have that field set, even though the engine boots with 4 cores. Two fixes:

- **Post-load default**: in `Settings_Load`, if `num_execution_cores` is < 1 after the parse, set to 4 (matches `ControllerConfig_Default`).
- **Live sync**: when `GUI_Panel_Settings` is called with a known `live_core_count > 0`, sync the widget value to the live count. The widget now reflects what the engine is actually running, not what the cfg file happens to say.

`engine_mode` has a similar problem (defaults to 1 in cfg but bool widget shows 0 if missing). Not patched in this pass — we can't distinguish "missing from cfg" from "explicitly written =0" without parser changes, and flipping a bool back to 1 would override user intent.
