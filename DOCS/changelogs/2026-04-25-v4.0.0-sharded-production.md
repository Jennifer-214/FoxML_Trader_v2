# 2026-04-25 (evening) — v4.0.0: Sharded production, per-core ML, hot-swap

Branch: `experiment/per-core-sharding` (now main). Marks the architectural pivot
from legacy single-threaded engine to per-core sharded as the production path.

Tags in order:
- `live-readiness-merged` — pre-c12 merge of `experiment/live-readiness`
- `sharded-production-ready` — c11 (sharded as default + live-readiness wired)
- `sharded-ml-loop-complete` — c16 (per-core ML confidence loop)
- `v4.0.0` — this release (= sharded-ml-loop + hot-swap + live-data wiring)

## Why 4.0.0 (not 3.8.0)

CLAUDE.md doctrine: "Major (X): architectural rewrites — new hot-path design."
This release flips the production-mode default from legacy single-threaded to
per-core sharded. Hot path goes from one ~5µs PortfolioController per tick to
N branchless ExecutionCore_Tick per core (40-400ns each, p99 target ≤500ns).
That's an architecture change, not a feature delta — bumping major.

## What ships in 4.0.0

### Sharded as production default
- `engine_mode=sharded` is the default in `ControllerConfig_Default`.
  Pre-existing `engine.cfg` files without an explicit `engine_mode` line now
  start in sharded mode automatically.
- `engine_mode=single_core` (legacy path) emits a runtime deprecation warning
  at startup. Legacy mode is preserved for benchmark/regression use only.
- `main.cpp` returns from `main()` after the sharded dispatch on the production
  path. Legacy code lives below the dispatch with a "LEGACY ENGINE PATH"
  visual marker block. This is load-bearing: see CLAUDE.md
  "Cross-Mode Init Placement (load-bearing — Phase 13+)" — anything new that
  needs to run in both modes must be wired BEFORE the dispatch in `main.cpp`
  OR have an equivalent path in `EngineSharded.hpp`.

### Per-core engine integration (c5–c11)
Brings sharded mode to feature-parity with the legacy live-readiness work
that shipped earlier in the day (depth recorder, notify, tick recorder,
maker/taker accounting, Phase 8 OMS hardening).
- c5: maker/taker fill counters live on `OrderManagerState` (entry + exit).
  Sanity invariant `total_fees == total_maker_fees + total_taker_fees`
  holds after every sync fill.
- c6: depth WebSocket thread + DepthRecorder init parallel to legacy. CSV
  rotation, gap markers, prune by `record_max_days` all work in sharded.
- c7: TickRecorder integrated into the producer fan-out. Daily CSV rotation.
- c8: NotifyState init with stderr/Command backend selection. `g_notify`
  global wired; backtest stays null (no-op).
- c9: explicit `oms.fee_rate_maker = cfg.fee_rate_maker` after `OrderManager_Init`
  so the legacy backward-compat-mirror in Init doesn't clobber explicit cfg.
- c10: maker/taker counter increments in `OrderManager_HandleFill` (BUY entry +
  SELL exit, gated on `o->is_maker`).
- c11: visual deprecation markers on legacy code paths (header comments,
  startup warning when `engine_mode=single_core`).

### Per-core ML confidence loop (c12–c16)
Phase 6prep ConfidenceScorer behavior was wired only into legacy mode pre-4.0.
This release ports it to the sharded production path so STRATEGY_ML cores
have the same armed-but-inactive-on-noise-floor safety net.

- c12: per-core `ConfidenceScorer` lives on `CoreContext`. `EventLoopState_Init`
  sets safe defaults; `EngineSharded_Run` re-inits with cfg
  (`confidence_window`, `confidence_freshness_tau`) for STRATEGY_ML cores.
- c13: entry-prediction tracking. `MLBuildContext` bundle pipes a
  `out_prediction` outparam through `Strategy_BuildParameters` to
  `ML_BuildParameters`. `EventLoop_RebuildAllParameters` wires it to
  `ctx->staged_prediction`. `drain_with_submit` snapshots staged → active
  at entry-submit time, so the IC update at exit pairs the realized return
  with the prediction that triggered the trade — not the latest rebuild.
- c14: `ConfidenceScorer_Update` on exit fill. `OrderManagerState` gains
  `last_closed_mask` + `last_realized_return[]`. `HandleFill` SELL branch
  sets the bit + stores return. `drain_confidence_feedback` runs after
  `OrderManager_Tick`, walks the mask, calls `ConfidenceScorer_Update` for
  each ML core, clears `active_prediction`, clears the mask.
- c15: confidence-damped threshold. `ML_BuildParameters` applies
  `effective_thr = base * (scale - conf)`, clamped ≤ 1.0, when
  `confidence_enabled`. Mirrors legacy at `PortfolioController.hpp:~1614`.
  Noise-floor IC clamps to `CONFIDENCE_MIN_IC_DEFAULT = 0.01` →
  effective ≈ 2*base → gate stays cold until real signal materializes.
- c16: `PerCoreSnap` gains `is_ml`, `ml_model_loaded`, `ml_last_prediction`,
  `ml_last_confidence`, `ml_confidence_ic`, `ml_confidence_rmse`,
  `ml_active_prediction`. `TUI_CopySnapshotSharded` populates per-core +
  aggregates the headline summary (s->ml.*) from the highest-confidence
  ML core. `GUI_Panel_MLIntelligence` gets a "Per-Core ML" collapsing
  section with a row per ML core (model status, prediction, conf bar,
  IC color-coded by sign, RMSE).

### Hot-swap strategy per core (4.0 new feature)
`EventLoop_RebuildAllParameters` sees a pending `swap_strategy_requested[c]`
on the slow path and applies it when `portfolio.active_bitmap` shows no open
position on that slot. A new "Per-Core Strategy" GUI panel offers a dropdown
+ Apply button per core, with status text showing pending vs ready. The
existing strategy's TP/SL still governs its own entry — the swap defers
until the position closes naturally so we never mix exit-side parameters
across strategies.

Mechanically: `pending_strategy_id` writes go through `__atomic_store` on
`TUISharedState::swap_strategy_requested[16]`. The controller thread's slow
path is the sole consumer. Reset to `STRATEGY_NONE = 0xFF` after applying.

### Live data wiring (build.sh)
`build.sh` now creates a symlink `<build_dir>/engine.cfg → ../engine.cfg`
on every build. Pre-4.0, running `./engine` from a build dir got
"config not found, using defaults" — and silently fell back to synthetic
ticks instead of the live Binance feed. This was a doc/devex bug. The
symlink fix makes "live data" the default path: any `./build.sh` variant
followed by `cd <build_dir> && ./engine_*` connects to live Binance unless
`sharded_force_synthetic=1` is set.

### Per-core config overrides + tabbed Settings UI (4.0 new feature)

Pre-4.0, the strategy-type tunings (`mr_tp_pct`, `momentum_tp_mult`, etc.)
were account-wide. Running two cores with the same strategy meant they
had to share TP/SL/spacing/etc. — meaningful A/B testing of the same
strategy with different tunings was impossible.

**`PerCoreOverrides<F>` struct** now lives on `ControllerConfig`. 18
overridable fields, names matching the same-named global members exactly:
- Trading: `take_profit_pct`, `stop_loss_pct`, `fee_floor_mult`
- Entry filters: `entry_offset_pct`, `volume_multiplier`,
  `spacing_multiplier`, `offset_stddev_mult`
- Strategy-specific: `simpledip_tp_pct/sl_pct`, `mr_tp_pct/sl_pct`,
  `momentum_tp_mult/sl_mult`, `emacross_tp_pct/sl_pct`,
  `ml_tp_pct/sl_pct/buy_threshold`

**Resolver:** `ControllerConfig_ResolveForCore(global, core_id)` returns a
stack-local copy with overrides applied. `EventLoop_RebuildAllParameters`
builds one per core per slow-path cycle. No strategy code needed to
change — they receive a fully-resolved cfg as before. Cost: ~12.5KB
struct copy + 18 conditionals per core per rebuild = ~250KB/sec at 4
cores × 5Hz slow path. Negligible.

**Cfg parser:** generic `core_N_<suffix>` matcher in
`ControllerConfig_Load`. Both pct and raw-FPN suffixes recognized.
Empty/0 = inherit global (matches existing strategy-type override convention).

**Tabbed Settings UI:** `[Global] [Core 0] [Core 1] [Core 2] [Core 3]`.
Number of core tabs follows `num_execution_cores` dynamically. Global
tab is the existing layout, untouched. Each Core tab is data-driven
from a new `per_core_fields[]` array — three sections (Trading / Entry
Filters / Strategy-Specific) with the 18 overridable fields. Editing
writes `core_<N>_<suffix>=<value>` into engine.cfg + triggers hot
reload via the existing reload_flag mechanism.

`engine.cfg.example` updated with a per-core overrides section
demonstrating syntax for all 18 fields.

**Adding a new override field:** extend `PerCoreOverrides` + the
corresponding line in `ControllerConfig_ResolveForCore` + a parser
case in `ControllerConfig_Load` + a row in `per_core_fields[]`.
Four sites, all in two files.

## What this enables

- Multi-core production with per-core strategy + per-core ML model. Risk is
  bounded per core (one bad core can lose its allocation, not the account).
- Sub-microsecond hot path per core — measured 40-400ns p99 on idle cores
  during boot smoke test, well under the ≤500ns sharded target.
- Live A/B testing by hot-swapping strategies on a subset of cores while
  others continue running their current strategy.
- Per-core ML observability — see prediction, confidence, IC, and RMSE for
  each ML core simultaneously. Headline summary picks the highest-conf core.
- Production-default safety: noise-floor ML model self-disables via the
  damped threshold; non-ML cores are unaffected.

## What didn't change

- Legacy single-threaded `PortfolioController` path remains fully functional
  for benchmark + regression. Tests still cover both modes.
- `engine.cfg` schema is fully backward compatible. No existing field was
  renamed or repurposed. New cfg fields default to behavior-preserving values.
- ANSI TUI renderer is unchanged; sharded mode renders to the same TUI as
  legacy. The new "Per-Core ML" + "Per-Core Strategy" panels are GUI-only.

## Known gaps (intentional, deferred)

- Cross-mode init placement is doctrine-only — there's no compiler check
  that catches new code added below the sharded dispatch in `main.cpp`. The
  CLAUDE.md "Cross-Mode Init Placement" section is the load-bearing rule.
- ConfidenceScorer math is `double` throughout (not FPN). See CLAUDE.md
  "FPN-Only Accounting" known-violations list. Not in scope for 4.0.
- Hot-swap only applies between rebuilds; there's no force-flatten path. If
  you want to drop a strategy with an open position, you wait for TP/SL or
  manually close. Sufficient for current use cases.
- No regression test for hot-swap mid-stream behavior. Shipped because the
  mechanism is small (atomic flag + bitmap check); can add when the feature
  has been exercised live.
