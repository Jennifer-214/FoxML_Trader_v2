# v5.4 Test Inventory — what we need to land to prevent regressions

Companion to `plans/2026-04-29-strategy-restoration-master.md` and
`DOCS/v5.4-regression-postmortem.md`. Lists every test class that must
exist by v5.4.0 ship to ensure (a) the fixes work and (b) future
sprints can't silently re-introduce the same class of regressions.

Tests grouped by what they protect against. Each group has a priority
label reflecting its actual load-bearing role:

- **MUST** — load-bearing for the v5.4 ship; without these we don't
  know if the fix worked. Required.
- **SHOULD** — credibility / reasonable cost / real value. Recommended
  but not blocking ship if any single one slips.
- **DEFERRED** — gold-plating for a solo project. Skip for v5.4; may
  ship later if priorities shift.

---

## Group A — Strategy lifecycle smoke tests (Phase 2) — **MUST**

**Protects against:** strategies being dispatched without their full
lifecycle wired (the F7-F10 class of bug).

**One test file per strategy:** `tests/strategy_lifecycle_test.cpp` (NEW)
or extend `controller_test.cpp` with a per-strategy section.

| Test name | What it asserts | Phase |
|---|---|---|
| `test_<strat>_init_allocates_state` | After `Strategy_InitPerCore(slot, STRATEGY_X)`, `ctx.strategy_state != nullptr` AND `ctx.strategy_state_kind == STRATEGY_X` | 2.1 (per strat) |
| `test_<strat>_init_idempotent` | Calling Init twice on the same slot frees + reallocates cleanly (no leak) | 2.1 |
| `test_<strat>_adapt_updates_state` | After Adapt with non-trivial market data, observable state field changes (e.g. `live_breakout_mult` for Momentum, `recent_high` for SimpleDip) | 2.2-2.5 |
| `test_<strat>_buildparams_reads_state` | BuildParameters output for state-default differs from BuildParameters output after Adapt | 2.2-2.5 |
| `test_<strat>_exitadjust_writes_ratchet` | After ExitAdjust on a synthetic open position, `state.cores[slot].pending_params.ratchet_sl` changed; `pos->stop_loss_price` unchanged (or only as cosmetic side-effect) | 2.2-2.5 |
| `test_<strat>_free_cleanup` | After `Strategy_FreePerCore`, `ctx.strategy_state == nullptr`; no valgrind/ASan errors | 2.1 |

Five strategies × six tests ≈ 25-30 assertions across Phase 2.

## Group B — Behavioral execution-layer tests (Phase 5.3) — **MUST**

**Protects against:** the dead-write pattern recurring. Catches "strategy
modifies field X but field Y is what execution actually uses."

**Test fixture:** stack-allocated `EventLoopState<64>` + `OrderManagerState<64>`
+ `ExecutionCore<64>` per test. Helper `get_effective_sl(core, active)`
mirrors `ExecutionCore.hpp:268+322` exactly.

| Test name | What it asserts | Phase |
|---|---|---|
| `test_effective_sl_trails_up_on_rising_price` | Open MR position; run 5 cadences with rising price; assert `effective_sl(t=5) > effective_sl(t=0)` | 5.3 |
| `test_effective_sl_respects_fee_floor_cap` | Same setup with tight `momentum_sl_mult`; assert ratchet_sl never exceeds `entry × (1 - 3 × fee_rate_taker)` | 5.3 (Momentum) |
| `test_effective_sl_unchanged_when_no_adapt` | If `_Adapt` is gated off (e.g. cfg flag), `effective_sl` stays at entry-time value | 5.3 |
| `test_pos_stop_loss_price_is_cosmetic` | After Phase 2 wiring, write to `pos->stop_loss_price` directly (bypassing strategy); assert `effective_sl` is unchanged. Documents that `pos->...` is no longer execution-affecting. | 5.3 |
| `test_effective_tp_trails_on_winning_position` | Same shape as effective_sl test but for TP via the new `cached_params.ratchet_tp` (Phase 3.3) | 5.3 + 3.3 |

## Group G — Calls-graph-diff (Phase 0.3 + Phase 6) — **DEFERRED** (keep tool, skip CI)

The `tools/calls_graph_diff.sh` script ships in Phase 0.3 — that's the
tool itself. CI integration as a blocking gate is **DEFERRED**. For a
solo-maintained project, manual quarterly invocation is sufficient;
making it block-on-fail would be more friction than it's worth.

**Protects against:** future architectural sprints orphaning functions
(the root cause of F1, F7-F10).

**Tool:** `tools/calls_graph_diff.sh` (NEW in Phase 0.3).

| Test name | What it asserts | Phase |
|---|---|---|
| `test_no_orphaned_functions_in_active_builds` | Run `tools/calls_graph_diff.sh` against current main; output is empty (no functions in legacy not also in sharded, OR explicitly marked "skipped — reason") | 5.4 (CI integration) |
| `test_strategy_lifecycle_completeness` | For each `STRATEGY_*` enum value, dispatcher entry exists for all 5 lifecycle stages (Init, Adapt, BuildParameters, ExitAdjust, RegimeAdjust) — or explicit SKIPPED marker | 6.4 |

## Group H — Dead-write detection (Phase 6.2) — **DEFERRED** (skill update only)

The /dust skill update ships in Phase 6.2 — that's the operator-invocable
audit. Automated blocking on fail is **DEFERRED**. Run /dust periodically
when prepping a release; don't enforce on every commit.

**Protects against:** new code introducing the dead-write pattern in
the future.

**Tool:** extension to `/dust` skill's audit scans.

| Scan name | What it flags | Phase |
|---|---|---|
| `dust_dead_write_audit` | For each struct field write, verify at least one execution-path read exists. Flags writes-with-no-readers as candidate dead-write. | 6.2 |
| `dust_orphan_function_audit` | For each `Pattern_FunctionName` in CODE_MAP, find call sites in active build configs. Functions with zero calls → candidate dead code. | 6.2 |
| `dust_field_read_flow` | For each struct field that's read in execution path, document which code path writes it. Reads-with-no-writers = uninitialized-read bug. | 6.2 |

## Group I — Performance regression gates (Phase 5) — **DEFERRED**

Existing latency table + manual GUI inspection covers the operational
need for now. Adding formal asserts is **DEFERRED** — would require
deciding what threshold counts as a "regression" which is genuinely
hard in a system with variable cache pressure.

**Protects against:** the 200µs → 1000µs slow-path regression class.

| Test name | What it asserts | Phase |
|---|---|---|
| `bench_slow_path_p99_under_500us` | Synthetic backtest with known tick volume; assert per-core slow-path p99 ≤ 500µs | 5 |
| `bench_hot_path_p99_under_1us` | Existing `bench_batch_floor` discipline; ensure Phase 2-3 changes don't push hot-path past 1µs p99 | 5 (extend existing) |
| `bench_rebuild_section_p50_under_50us` | `slow_path_breakdown[REBUILD]` p50 stays under 50µs after strategy lifecycle is wired in (state-driven adapt should be fast) | 5 |

## What this inventory is NOT

- Not a comprehensive coverage strategy. Doesn't try to test every code
  path in every strategy — just the ones that protect against the F1-F10
  class of bugs.
- Not a replacement for backtest validation. After each Phase 2.X strategy
  wiring, a backtest comparison (run a known dataset on legacy vs sharded,
  eyeball results) is the primary "did we break it" check. Unit tests
  catch specific contract violations; backtests catch behavioral drift.
- Not a perf-tuning suite. Group I prevents regressions but doesn't try
  to optimize. Optimization is a separate concern (v5.5.x latency
  reduction).

## Operational role of this doc

Living document. As v5.4 phases land, update each row's status (✓ green
when shipped, ⚠ when partial, ✗ if cut from scope). At v5.4.0 release,
this is the artifact that documents what we actually shipped vs planned.

For future architectural sprints (the v6.x or v5.5.x next-time-this-pattern-recurs
scenario): this doc + `DOCS/v5.4-regression-postmortem.md` together are
the prior art. Read both before doing similar work.
